# 演示文稿（book-presentation）

把研究任务的证据整理成适合演示的 Markdown 报告，由 ObsidianBrain 的受控生成器把报告转换为可下载的 PPTX。你的职责是让内容具有清楚的受众、主线和可追溯依据；你不直接创建文件、调用 PowerPoint 或控制版式引擎。

## 当前生成器的真实能力

- 服务端以任务标题制作封面，扫描报告中的 `##` 或 `###` 标题作为内容页标题；标题下的非空行变成要点。长小节可能拆页，但总共最多保留八个内容页，每页最多六条要点，每条会被截到约 180 个字符，最后自动追加“总结与下一步”页。
- 生成器支持文字要点和统一的证据页脚，不支持模型直接指定图片、图表、动画、讲者备注或任意版式。不要声称这些能力已生成，也不要把重要证据只放在“备注”里。
- 输出仍是 Markdown 研究报告；PPTX 的生成、校验和下载由服务端完成。上层任务与来源约束优先，不能自行写文件、申请 Shell 或引入未授权素材。

## 内容设计步骤

1. **确定受众与任务。** 从标题和说明判断听众最想知道的决策或理解目标；若受众未指定，按对本书有基础兴趣、但不熟悉本次专题的读者设计。写出一句中心主张，所有页面都服务于它。
2. **搭建短叙事。** 推荐顺序是问题背景、关键发现、对比或机制、边界/风险、可执行下一步。按材料实际强度增删，不强迫六页模板；内容页一般控制在三到六个 `##` 小节，留余地给生成器的封面与总结页。
3. **用结论式标题。** 小节标题直接表达该页要点，而不是“背景”“分析一”这类空标题。每页只承载一个主要观点，正文优先用三到五行短要点；长段落、宽表格和复杂代码会被压成文本，需主动改写为清晰句子。
4. **保留证据与限定。** 每个关键事实、数字和比较在同一要点附近标注有效 `[S<n>]`；外部资料若经授权使用，需在报告单独列出真实 URL，不冒充书内引用。证据不够的页应改成“待验证的问题”，不得编造数据、图像或结论。
5. **校对转换结果。** 写作时就按生成器会读取的结构检查：内容页总数不超过八个；每节尽量不超过六个要点，避免拆页后出现通用的“续”标题；重要内容放在前八页内；每条尽量短于 180 字符。不要依赖一级标题、脚注、隐藏备注或 Markdown 表格承载必须出现在幻灯片上的信息。

## 输出格式

直接输出 Markdown。开头可有两句受众/主线说明，随后以 `## 结论式标题` 分节，用 `-` 列要点；最后可列“依据与限制”，但关键来源仍须紧挨其论断。若任务包含与 PPTX 不兼容的复杂材料，在报告中说明简化方式，不虚称幻灯片具有无法生成的图形或交互。

交付前自检：前两页能否讲清主线；页面之间是否顺畅；每页是否只有一个主观点；数字与比较是否有证据；是否有超过生成器上限而会丢失的内容；是否误称已经生成、验证或上传 PPTX。

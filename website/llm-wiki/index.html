OBSIDIANBRAIN / LLM WIKI ARCHITECTURE

LLM Wiki 架构剖析

书籍知识库、Wiki 工作台、知识问答和研究任务不是四个孤立页面，而是同一条管线的四个工位：来源同步产出不可变证据，语义编译把证据炼成候选知识，人工审核放行入库，问答与研究再消费这些知识——研究结论又能回流为新的候选。本页按数据流动的顺序，逐层剖析这条闭环的实现。

00 / OVERVIEW

总览 — 一条管线，四个工位，一套边界

Book Wiki 的架构目标可以压缩成一句话：数据库原生、每书隔离、由 DeepSeek Harness 驱动、被审核门禁保护的 Markdown 书籍知识系统。它建立在四条不可妥协的边界之上：

  1. 1
    原书是只读来源，不是 Agent 工作区

    整条管线从头到尾不会写回或改写任何 Markdown 原文件；Agent 也不直接读文件，而是通过受控工具读取数据库里的来源片段。

  2. 2
    SQLite 是生成知识的唯一事实来源

    实体、论断、关系、引用、版本、审核记录、运行审计全部落在本机 brain.db，不与任何 Markdown Wiki 双写。

  3. 3
    Rust 后端拥有全部业务状态与权力

    检索、提示词组装、JSON 契约校验、审核门禁、配额、事务和 PPTX 渲染都在 Rust 侧；后端是唯一能写数据库的角色。

  4. 4
    Harness 只负责 Agent 执行，不拥有知识数据

    DeepSeek Harness 是文本进出的一次性 ACP 子进程，从不接触数据库路径；它的一切产出都只是 proposal（候选提案）。

管线全景

01来源同步Markdown → 不可变 version / span + FTS5 索引
02语义编译受审计 ACP Run，增量、分批、严格 JSON 契约
03变更集候选knowledge_change_sets，状态 proposed
04人工审核服务端复验 + 单事务原子写入正式知识
05消费与回流带引用问答 / 研究任务，产出再成候选

四个页面对应管线上的不同工位，彼此通过深链咬合：书籍知识库（/knowledge）是入口与编译编排台，编译完成后「查看并审核」直接跳转 /knowledge/wiki?review=<变更集>；Wiki 工作台（/knowledge/wiki）承载知识资产浏览与全部审核动作；知识问答（/knowledge/chat）消费正式知识并支持把回答保存为候选、跳回工作台审核；研究任务（/knowledge/tasks）做深度加工，研究结论同样以候选身份进入审核队列。第五个页面 Wiki 配置（/knowledge/settings）为整条管线供应 Runtime、模型供应商、配置文档与 Skill。

「一切皆 proposal」的写入模型

Agent 对知识的唯一写入通道是 knowledge_propose_changes 类工具——它只创建 proposed 状态的变更集；只有用户在审核界面触发 resolve_knowledge_change_set（approve）才把变更写进正式表。人工编辑（工作台改实体、合并、拆分）与阅境轩划线入库也走同一变更集通道，被标记为 human_protected 高风险候选，同样要经过审核。系统里不存在任何绕过审核直接写正式知识的路径。

01 / SOURCES

来源层 — 书籍知识库与不可变证据

管线的第一站是把一个 Markdown 文件夹变成可检索、可追溯、可重复同步的证据库。这一层完全由 Rust 完成，不涉及任何模型调用。

每书一库，硬隔离

knowledge_bases 与书架表 reader_books 一对一（book_id UNIQUE），且只允许 kind = folder 的 Markdown 书籍建库——前端书选择器与后端初始化都执行同一过滤，PDF 停留在阅读器不进 Wiki 工作流。所有知识表都携带 knowledge_base_id，唯一约束与查询索引必须带该字段，跨书访问在数据模型层就被拒绝。生命周期由 lifecycle 枚举控制（uninitialized / active / paused / archived），读写边界在 Store 层而非页面层执行：只有 active 才能创建任务、启动 Run、生成或处理变更集，暂停/归档保留只读查询。

三层来源模型：document → version → span

表职责关键约束
source_documents一个 Markdown 文件的登记项：路径、标题、序号、当前版本指针、sync_status（current / changed / missing / failed）(knowledge_base_id, original_path) 唯一
source_versions文件的一次内容快照：content_hash、字节数、抽取状态相同来源相同哈希不得重复建版本——重复同步天然幂等
source_spans版本切出的不可变片段：标题、锚点、line_start / line_end、正文、content_hash、token 估计(knowledge_base_id, source_version_id, ordinal) 索引，顺序稳定

同步（sync_book_knowledge_base）递归扫描 .md / .markdown 文件（忽略 .git、.obsidian、node_modules 等隐藏与构建目录，单文件超过 10MB 跳过，目录深度上限 24 层），按内容哈希对比建立 added / changed / missing 集合，只抽取新增和变化的文档；编译进行中会拒绝同步。三层 ID 全部由稳定哈希派生（如 version_id = SHA-256(source_id + content_hash)），内容不变则 ID 不变——这是重复同步幂等的根源。整个落库在单事务内完成：来源三表、两张 FTS 索引、章节镜像条目与引用一起写入，索引与核心表不会失配。

两个细节决定了后续检索的形状：文件更新不会级联删除旧证据——旧 version 与 span 保留，历史引用始终能落回当时的原文；文件删除只标记来源 missing，相关知识进入影响评估，原书永不改写。每个 span 会同步生成一条 entry_type = source_section 的章节镜像条目（status verified、confidence 1.0）进入同一实体索引——它就是问答检索里「章节兜底」层的载体（见第 05 章）；来源更新后不再指向当前版本的镜像条目被置为 stale，退出检索。

FTS5 全文索引与中文二元组

检索不用向量库，而是两张 SQLite FTS5 虚表：knowledge_entries_fts（title / aliases / summary / content_md / tags / cjk_terms）与 source_spans_fts（source_title / heading / content / cjk_terms），tokenizer 为 unicode61。unicode61 无法切分连续中文，因此写入时扫描 CJK 码点段（基本区、扩展 A、兼容区），把每段连续中文切成相邻字符二元组存入 cjk_terms 列；查询侧用同一规范化函数生成二元组并保留完整中文词，与 ASCII 词一起取前 32 个词做 OR 查询，再与标题/别名精确命中和前缀结果合并加权——只改查询不索引二元组是明确禁止的错误实现。FTS 写入与来源/实体事务绑定，保证索引与核心表一致；升级库在首次检索时一次性重建旧索引。规模上做过十万 span 的显式验证：实体分页下推为 SQLite LIMIT/OFFSET，FTS 命中不足时不再做正文 LIKE 全表扫描补位。

页面如何呈现这一层

「书籍知识库」页是纯卡片列表：每书一卡，展示 sync_state（clean / outdated / scanning / extracting / ingesting / failed）、编译状态与生命周期徽章、来源/实体/论断/任务计数。「同步」按钮只在 active 且原书路径可用且非编译中时可用；书架目录被移动或删除时卡片显示「原书目录已失效」并禁用同步与编译——同步与编译在后端也会实时复查书架路径。

02 / COMPILE

语义编译 — 受审计的增量炼化

智能编译是整条管线里唯一「无中生有」的环节：把跨章节的来源片段炼成主题实体、论断与关系。它的设计围绕三个词：增量、受审计、契约严格。

后台化：请求只入队，运行与 HTTP 解耦

compile_book_knowledge_base 前置要求 sync_state = clean，以 WHERE compile_state != 'compiling' 原子抢占后立即返回（重复触发会得到「已经在后台执行」的明确报错），实际编译由独立 Tokio 任务执行；后台 Supervisor 捕获异常退出并落库为失败。知识库摘要上持久化了完整的运行投影：compile_phase（准备 → 连接 Runtime → 思考 → 工具 → 生成 → 校验 → 重试 → 收尾 → 待审核等阶段）、来源与批次进度（compile_processed_sources / compile_total_sources、compile_current_batch / compile_total_batches）、每 15 秒一次的心跳和取消标记。前端每 2.5 秒轮询摘要（带 canFocusDocument 守卫，后台标签页不轮询），因此离开页面不会中断编译；取消写入持久化请求并通知活跃 ACP Run。服务重启时仍处于 compiling 且不在待审核态的历史记录被转为明确失败，允许重新编译而不是永远转圈；waiting_review 的记录则被保留——它的变更集还在等人处理，重启不应把它误判为中断。

增量：检查点 + 编译指纹

knowledge_compile_checkpoints 记录每个来源文档已编译到的版本；编译只读取检查点缺失或版本不同的来源，变更集创建成功后推进检查点。检查点之上还有一层 compile_fingerprint，由四部分构成：

  • 编译协议 revision 与强制规则 / JSON Schema 的内容哈希（compile.md + semantic-output.schema.json）；
  • Runtime Profile 与模型（换了模型等于换了「编译器」）；
  • 生效配置文档的内容哈希（书籍规则变了，旧候选不再等价）；
  • 实际启用 Skill 的 revision 与内容哈希。

准备和执行阶段都按当前指纹查询待编译来源：任一输入变化会让全书来源重新进入编译；指纹相同则只处理内容版本变化的来源。与之配套的关键补偿是：驳回候选会删除对应来源的编译检查点——否则被驳回的来源将带着检查点被永久跳过，再也得不到重新分析的机会。

分批与预算：把上下文花在刀刃上

参数值动机
单批来源正文预算动态计算：32,000 字符 Prompt 总预算扣除协议、Skill 与配置固定开销后，clamp 到 [1,000, 20,000]；单个片段切块上限 8,000 字符超长章节继续切块而不是静默截断；所有分块正文完整发送
单批候选上限5 个跨片段归并后的高价值条目强制模型做归并取舍，避免碎片化候选
输出上限首次 8,192 token，恢复调用 12,288 token通过 Harness 供应商 Patch 设置
重试策略每批合计最多两次模型调用（空正文恢复与 JSON 修复共享一次额度）；拒绝回答与用户取消不重试成本可控、失败可解释
单批截止180 秒防止悬挂 Run 占用队列
供应商自动重试编译路由从默认最多 5 次压缩为最多 1 次，并显式关闭推理等级只作用于编译，不影响问答与研究

每批还会读取已有语义 Wiki 和前批候选注入 Prompt，让模型能跨批次归并概念、别名、论断与关系，而不是每批各说各话。

契约：semantic-contract-v4

编译输出协议由 backend/prompts/wiki/compile.md（强制规则）与 semantic-output.schema.json（同时用于提示词展示与 Rust 侧 JSON Schema draft-07 校验）双端锁定，协议 revision 常量与两份文件的内容哈希都计入编译指纹，硬协议优先级高于书籍配置和 Skill。核心约束：

  • 顶层单一 JSON 对象，entries 最多五项，必填类型、枚举、文本长度、数值范围全由 Schema 检查，额外字段拒绝；
  • 每条目和每条论断必须显式引用本批 span ID，论断引用必须包含在条目引用中；关系只能指向已提供的主题或本批候选，禁止自连、重复 slug 和猜测目标；
  • entries: [] 必须附具体 no_material_reason——「本批无实质新增」写入运行事件并走 no-material 审计流程（创建状态为 applied 的 no_material 变更记录，照常推进检查点），不凭空制造知识；
  • 模型只返回短摘要、别名、原子论断、关系和引用，不撰写 content_md：可检索正文由服务端根据摘要和论断生成，并再次执行字段限长；
  • 解析器只接受一个完整 JSON 对象；截断、非法转义、字段/引用错误进入带具体字段路径和校验原因的修复重试，不允许「取第一个对象就算成功」或字符串替换猜测；最终失败不写检查点。
🔍为什么编译 Run 零工具：来源批次已完整内联进 Prompt，变更集由 BookWikiService 直接校验和持久化，挂载 MCP 工具目录只会带来无用的工具发现、Schema token 和额外 Agent 回合。这是「按任务类型裁剪工具目录」原则的极端案例（另两个零工具 Run：演示策划见第 06 章，Skill 基准见第 07 章）。

审计：每一次模型调用都可回放

编译以受审计 Run 执行（run_audited）：启动 Runtime 前把最终有效 Prompt、稳定哈希、字符数、Skill 与配置内容快照、工具白名单和证据引用写入 agent_run_inspections，与 Run 一对一且运行后不随当前配置变化；执行过程的事件（阶段、重试、停止原因）落入 agent_run_events。校验通过的候选写入 knowledge_change_sets，等待第 03 章的审核门禁。

03 / REVIEW

审核入库 — 变更集状态机与原子应用

候选与正式知识之间隔着一道双向门禁：模型不能直接写入，人也不能绕过审计直接改库。这道门由变更集（change set）实现。

数据模型与状态机

表 / 字段取值说明
knowledge_change_sets.statusproposed → applied（批准即原子应用）/ rejected（驳回），revision 冲突时 conflicted集合级状态；附 risk_level（low / medium / high）、创建它的 agent_run_id、全局唯一 idempotency_key、解决时间与解决者，以及分类汇总 / 引用审计 / 级联影响三份 JSON 快照
knowledge_changes.operationcreate / update / merge / split / archive / restore逐项变更（对象类型 entry / claim / relation）；带 expected_revision 乐观并发和 before_json / after_json 差异，按 ordinal 有序
变更分类new / update / disputed服务端根据正式实体是否存在复核 new/update，只有模型显式声明才允许 disputed；争议变更应用后其论断以 disputed 验证状态保存
knowledge_reviewspending → approved / rejected与变更集一对一的人工审核单，保存审核说明与裁决时间

批准时发生什么

resolve_knowledge_change_set（approve）不是简单翻状态：服务端再次校验来源与 expected_revision，复核引用审计，然后在一个 BEGIN IMMEDIATE 事务中写入条目、论断、关系、引用和版本快照——变更应用器必须先验证整个集合再全部提交，禁止部分成功；任何 revision 冲突让整组变更失败并标记 conflicted。实体、引用与 FTS 索引在同一事务内保持一致。迁移、知识库删除和达到五十项的大变更集应用前还会自动创建数据库快照（默认保留 7 份）。

合并与拆分的精确语义

  • 合并：候选携带目标与全部来源实体的期望 revision；事务内先保存版本，合并引用、论断与出向关系，归档来源实体，并把未参与合并实体的入向关系重定向到目标。
  • 拆分：同一事务归档原实体并创建 2–12 个新实体，新实体继承原始引用，但不自动复制未经核验的旧论断和关系。
  • 人工编辑：工作台的编辑/合并/拆分与阅境轩划线入库都创建 human_protected 高风险变更集；摘录必须重新定位到当前 source span，无法定位时拒绝伪造引用。

审核界面呈现的证据

工作台审核弹窗一次展示一个变更集，除了标题、理由与风险徽章，还有三格审计摘要：变更分类计数（new/update/disputed）、引用审计（条目引用、显式论断引用与继承引用的统计，未通过时「批准并应用」按钮被禁用）、级联影响（生成候选时冻结的现有论断/关系/引用数量，让你知道批准会波及多大范围）。逐条变更卡片提供 before/after JSON 差异。批准后可选填审核说明，全程写入审计。

⚖️诚实的边界：结构校验只能保证契约与引用范围合法，不能证明自然语言事实正确——事实核验始终靠人。这也是为什么模型返回空候选时系统宁可记 no_material，也不伪造待审核内容。
04 / WORKSPACE

Wiki 工作台 — 知识资产的读侧与体检

审核放行的知识落入四张正式表，Wiki 工作台是它们的读侧门面与人工维护入口。

正式知识的数据模型

表内容关键约束
knowledge_entries主题实体：entry_type（无 DB 级 CHECK，服务端枚举九种语义类型 entity / concept / method / event / comparison / synthesis / question / answer / overview，另有系统生成的 source_section 章节镜像）、slug、标题、摘要、服务端生成的 content_md、status（draft / verified / stale / archived）、edit_policy（agent_managed / human_protected）、置信度、revision(knowledge_base_id, entry_type, slug) 唯一；别名在 knowledge_entry_aliases，历史版本在 knowledge_entry_versions
knowledge_claims原子论断：主语实体 + 谓词 + 宾语（实体或文本）、论断文本、置信度、有效期verification_status：unverified / supported / disputed / rejected / stale
knowledge_relations实体间关系：类型、强度、证据(from, to, relation_type) 库内唯一；禁止跨库关系
knowledge_citations实体/论断 → source span 的引用：原文摘录、相关度citation_role：supports / contradicts / context——引用可以支持也可以反驳

读侧实现要点

  • 列表：list_knowledge_entries 分页下推为 SQLite LIMIT/OFFSET（每页 60，响应带 offset / limit / total / has_more），搜索走 FTS5 加权（标题 > 别名 > 摘要 > 正文），输入 220ms 防抖。
  • 详情一次拿全：get_knowledge_entry 单个调用返回正文、论断、关系、引用（含来源路径与行号区间）和版本历史——没有为每个子资源单设工具，减少往返。
  • 正文渲染：复用阅境轩的共享 Markdown 管线（公式、表格、Mermaid、代码高亮），实体正文与问答预览走同一条渲染链。
  • 关系图谱：洞察接口返回连接枢纽（按度数）、孤立实体与关系总数；路径查找是限定单库的有界 BFS（服务端最多八层，工作台默认查五层）；桌面画布快照只取连接度最高的至多 120 个节点，前端做纯 SVG 静态布局（度数最高者居中、环形分布、滚轮缩放、拖拽平移），关闭弹窗即卸载快照；手机端不请求画布，只用洞察与路径接口。

知识体检：零模型的确定性 lint

lint_book_knowledge_base 是纯确定性检查：来源完整性、语义层覆盖、实体引用有效性、论断直接证据、重复标题。它不调用模型、不修改任何知识，输出 healthy / warning 状态、语义实体与来源片段计数、待审核数量和逐条 issue（severity + 说明）。把「质量检查」做成确定性规则而非又一次 LLM 调用，是这套系统一以贯之的取舍：能用代码验证的绝不花 token。

05 / QA

知识问答 — 证据在手的流式回答

问答是管线的主要消费端。它的核心承诺：回答带着可点开核验的引用，且一次问答严格限定在一本书内。

单次问答的完整链路

保存用户消息（单事务：用户消息 + 助手消息占位 + 会话范围）
  → 确定显式知识库范围（conversation_scopes 记录参与查询的库）
  → Rust 预召回：正式语义条目排在 source_section 之前，章节证据兜底
  → 建立上下文预算（证据按剩余预算公平分配，不由第一条长文独占）
  → 启动 Harness Run（能力令牌授权同书检索工具）
  → Agent 按需继续调用检索工具补查
  → SSE 流式生成，增量事件同步落库
  → completed：保存最终回答与有序来源引用

检索是「Rust 预召回 + Agent 按需补查」的混合模式：后端把上一轮与本轮问题拼接成检索词（消解「它」「这个」式指代），经 FTS5 预召回至多 8 条证据——SQL 排序让语义条目恒在前、source_section 章节镜像恒在后，「语义 Wiki 优先、章节证据兜底」由排序天然实现；每条证据以路径、行号、entry_id 和按类型区分的证据提示注入 Prompt，预算按剩余空间公平分配（单条上限 6,000 字符），不由第一条长文独占。召回为空时明确报「没有可用于回答的证据」，绝不无证据硬答。之后 Harness 凭能力令牌在同一本书范围内按需补查——任何检索工具都从 Run Capability 读取范围，不接受 Agent 自由传入其他知识库 ID。

[S#] 引用契约

预载条目按 [S1] [S2] … 编号并保存来源卡片快照。Prompt 明确限定模型只能使用本轮真实编号；工具补查但未预分配编号的资料必须列出真实 entry/span ID、标题和路径，不得伪造新编号。前端渲染答案后遍历文本节点，把 [S#] 替换为可点按钮（跳过代码块、公式和 Mermaid），点击打开来源预览弹窗——渲染实体正文与原文引用（路径 + 行号），只有用户点击弹窗中的明确操作才跳转 Wiki 工作台或阅境轩，核对证据不丢问答上下文。

SSE 实现细节

  • 问答流不是 EventSource，而是 fetch POST knowledge/chat/stream + response.body.getReader()，自研解析器按空行切块、聚合多行 data、处理跨 chunk 换行。
  • 事件序列：evidence（证据列表先行）→ run_started → text_delta / phase / tool_started / tool_finished / usage → completed（最终答案 + run_id + 证据）或 error。
  • 增量文本经 rAF 分帧缓冲吐字（尊重 reduced-motion），完成后以最终答案校正正文与来源；思考类 chunk 只映射为「正在分析」阶段，不保存不展示模型内部推理。
  • SSE 连接断开会触发问答 Run 取消——流式问答是前台活动；持久化的 agent_run_events 仍是审计与恢复的事实来源。
  • 会话历史：继续会话最多取最近八条消息（每条截断至 480 字符）辅助理解指代，但历史不能替代本轮召回的数据库证据；会话与消息保存在 SQLite（Harness Session ID 仅作诊断关联），页面加载即恢复最近会话。
  • 引用快照防漂移：knowledge_message_citations 不只存条目 ID，还冻结当时的 entry_revision 与标题、类型、摘要、状态、来源路径等九个快照列——实体日后被修订，历史回答里的来源卡片仍显示提问当时的模样。

回流与降级

「保存到 Wiki」调用 save_knowledge_answer，把完成的回答存为待审核 synthesis 候选变更集（带幂等键，Run 必须属于本书且已完成）并直接跳转审核弹窗；保存前回答引用的条目会被重新映射到当前版本的 span，来源已过期时拒绝保存并提示重新提问——问答的好答案由此回流进知识资产，但仍要过第 03 章的门禁。Runtime 不可用或流式失败时，页面降级为「证据检索模式」：只用 list_knowledge_entries 返回书内证据卡片，明确告知没有生成回答，不假装智能。

06 / TASKS

研究任务 — 租约队列、能力令牌与本地 PPTX

研究任务是管线的深度加工工位：长时间运行、可离开页面、可取消重试、可授权有限外网、可产出可编辑 PPTX。

耐久队列与租约

  • knowledge_tasks 是 SQLite 耐久队列：创建后 execute_knowledge_task 只入队，HTTP 立即返回；进程内单 Worker 按下次尝试时间、更新时间和创建时间领取，默认全局并发 1。
  • 领取时原子建立 45 秒租约（lease_expires_at），执行期每 15 秒心跳续期；租约过期任务重新排队，避免进程崩溃后任务丢失或双领。
  • 失败按 5 秒起始的指数退避重试（attempt_count / max_attempts / next_attempt_at），耗尽三次进入 failed；部分唯一索引保证每个知识库最多一个 running 任务。
  • 服务启动时把中断的 running 恢复为 queued（已请求取消的恢复为 cancelled）；取消经 watch 通道即时发送 ACP session/cancel，子进程组随连接回收。
  • 幂等：每次尝试生成独立 run_id，业务动作使用 task_id + attempt + phase 幂等键，Harness 重试只能重复提交同一候选，不能重复应用。
  • 结果回写：任务完成前，研究结论自动提交为 synthesis 候选变更集（confidence 0.68，带幂等键），状态投影在任务行的 knowledge_change_state 列——研究的产出回流知识库，同样必须经人工审核。

任务状态机为 draft → queued → running → completed / failed / cancelled，类型有三种——research（专题研究）、refresh（知识刷新）、review（事实审核），提示词各有侧重：refresh 区分「有旧版依据的变化」与「当前观察」，review 按支持/反对/条件成立/证据不足逐项核验。交付物可选 report 或 presentation，任务行上另有 artifact_state（not_requested / pending / ready / failed）与 knowledge_change_state（none / proposed / applied / rejected）两个投影列。前端每 1.2 秒轮询任务列表（同样受 canFocusDocument 守卫），运行中展示最近一条真实运行事件作为活动行。

Run Capability：令牌即权限

每个 Run 创建高熵随机能力令牌，SQLite 只保存 SHA-256（agent_run_capabilities）。Harness 侧插件经 127.0.0.1 专用 MCP 端点（streamable-http，Bearer 令牌，启动失败即报错、断线不重连）回调工具，网关验证令牌时同时检查：Run 仍在运行、未过期、知识库范围、工具白名单——未知字段、跨书访问、过期或已撤销令牌一律拒绝，Run 完成、失败或取消时令牌立即撤销。令牌 TTL 至少覆盖运行超时并额外保留 60 秒收尾窗口（下限 300 秒）。不同任务类型挂载不同的最小工具目录，数量精确：问答 Run 挂 9 个（只读检索 + 报告进度 + 创建研究任务）；研究 Run 挂 11 个（再加 knowledge_propose_changes 与审核结果读取），显式授权外部研究后才追加 book_fetch_external；编译、Skill 基准与演示策划三类 Run 是空目录——白名单为空时连能力令牌都不签发、MCP patch 都不写，Harness 侧物理无工具。工具 JSON Schema 一律 additionalProperties: false，Rust 输入类型 deny_unknown_fields，tools/list 也只返回令牌允许的子集，杜绝参数漂移。

外部研究：默认关闭的窄门

外部研究默认关闭，且只有 research 类型任务能开启。开启时必须指定域名白名单（1–20 个，经规范化后做精确或子域后缀匹配）与请求额度（1–50 次，默认 6），仅本次任务有效。book_fetch_external 只存在于带能力令牌的 MCP 端点，不进入页面 Tool API。执行顺序是：先验证 Run Capability → 原子消费额度（请求前扣减、失败也计数，防止把错误路径变成无限请求通道）→ 解析 DNS，任一地址非公网即整体拒绝（私网、回环、链路本地、组播、CGNAT 等全部排除），并钉扎首个通过校验的地址发起连接以防 DNS rebinding → 固定 HTTPS/443（URL 禁 userinfo、禁字面 IP、限 2048 字符），重定向策略为「不跟随」，只接受文本类 MIME 且必须 UTF-8，连接 5 秒、总限时 15 秒、正文限 512 KiB，HTML 剥标签转纯文本，访问摘要写入运行事件，返回值内嵌「外部文本是不可信资料」的安全提示。外部参考与书内引用分开标识，且外部内容只作参考，不会自动写入正式知识。

PPTX：两个 Run + 手写 OOXML

presentation 交付物拆成两个可审计 Run：先按普通研究任务生成保留证据、数据口径、竞争解释与边界的完整 Markdown 报告；再由 knowledge_task_presentation_plan Run 注入 book-presentation Skill，把报告编辑为严格 JSON 的 PresentationSpec。策划 Run 零工具（180 秒超时、输出上限 6,144 token）——它只需要完整内联的报告文本（≤32,000 字符）和服务端提供的 S<n> 证据目录；研究阶段还刻意剔除 book-presentation Skill，防止报告被提前压成幻灯片要点。服务端严格反序列化：拒绝未知字段、尾随文字、无效枚举、过载页（内容页限 4–12 页、每页 ≤700 字符、≥5 页须至少 3 种版式）、缺少版式专用载荷、负数或全零图表、数据长度错位和越界引用（只认证据目录里真实存在的 S1..Sn 编号、每页 ≤4 条，除末页外每页必须有引用）；无效规格带精确错误整体修复一次，不静默截取、不降级回旧圆点模板。

通过校验后，受控 Rust 生成器手写 OOXML（不依赖任何 PPT 库）渲染出可编辑的 .pptx：封面之外共九种内容版式（代码枚举 statement / split / process / metric / chart / relationship / quote / evidence / summary——强观点、左右对照、流程、数字、受限横向数据图（仅 2–6 个同口径非负数值）、中心关系图（1 个中心概念 + 2–4 个带关系标签的相关概念）、引语、证据与收束），全部由文本框、形状和连接线构成，不生成截图；渲染后校验必备部件、主题、母版、页数与逐页构图标记。二进制存入应用受管 artifacts 目录，knowledge_artifacts 表保存哈希、大小、校验状态（pending / valid / warning / invalid）与结构化校验详情，knowledge_artifact_citations 冻结引用当时的条目 revision 与标题快照；结构化质量报告——总页数、版式分布、引用覆盖率、主题（editorial / midnight / sage）与五项固定检查（演示规格、证据覆盖、构图多样性、PPTX 包结构、可编辑对象）——由前端直接展示，并可直接进入策划 Run 的检查器。

🛟失败不吞成果：演示策划、修复或渲染失败时任务标记为 failed 并允许重跑，但 result_summary 保留已完成的 Markdown 研究报告并在顶部附加失败原因；前端对这类任务优先开放「查看报告」，不因二进制交付失败而隐藏已完成的研究内容。

运行检查器：每次 Run 的飞行记录仪

run_audited 在启动 Runtime 前写入 agent_run_inspections 不可变快照：实际发送的最终 Prompt、稳定哈希与字符数、当前生效配置文档（ID/作用域/revision/正文）、选中 Skill（slug/revision/指令/应用方式 declared_only 或 prompt_injected）、工具白名单与显式证据 ID。任务详情的「运行检查器」把快照与 agent_run_events 时间线组合展示——任务为什么得出某个结果，可以逐字追查。历史运行允许没有快照，界面如实显示而不是推测当时的 Prompt。

07 / CONFIG & SKILLS

配置与 Skill — 指纹的另一半

第 02 章说过，配置文档与 Skill 的内容哈希是编译指纹的组成部分——这一章解释它们如何被管理和注入。

Runtime Profile 与多模型供应商

Runtime Profile 保存 ACP 启动命令（固定版本，如 npx -y @deepseek-ai/dsh@0.1.5-rc.1 --profile acp）、可选的供应商绑定与模型覆盖；「验证已保存配置」会真实启动 Runtime 完成一次请求（190 秒超时）后才显示连接已验证。模型供应商支持三种明确协议：openai-completions（OpenAI Chat Completions）、openai-responses（OpenAI Responses）、anthropic-messages（Anthropic Messages），经 Harness 的通用适配器注入。供应商独立存于 llm_provider_profiles 表，Runtime Profile 通过 provider_id 外键绑定（RESTRICT，防止删除仍被引用的供应商）。凭据来源二选一（credential_source）：系统凭据库（keychain，密钥以固定环境变量名注入 ACP 子进程环境，不落盘），或环境变量名（environment）——数据库只保存变量名 api_key_env 与「已配置」标记，密钥值只存在于启动后端进程的环境中，此模式下页面内联输入密钥会被服务端直接拒绝。写进 Harness 的 Provider Patch 永远只有元数据和变量名，API Key 值永不物化到任何临时文件；有界任务（编译、基准、策划）的 Patch 还会注入输出上限并关闭推理与多余重试。被禁用的供应商立即持久化，防止仍被 Runtime 选中。

配置文档

purpose / schema / instructions / AGENTS / CLAUDE 等配置文档以稳定 document_type 标识（不以文件名为键），分全局与书籍级作用域，保存在 SQLite 版本表并带 revision 乐观锁；运行时才物化为隔离临时目录里的文件。配置解析按「系统默认 → 场景模板 → 知识库覆盖 → 单次运行覆盖」合并为不可变 EffectiveWikiConfig，运行开始后不受配置页面修改影响。

Skill 体系：只注入指令，不放大权限

  • 七个内置 Skill：book-ingest（智能编译）、book-query（问答）、book-research（研究）、book-lint（质量检查）、book-presentation（演示交付）、book-synthesis（跨章节综合）、markdown-collection（非传统章节式文集）。内置正文只读，「复制为自定义」生成独立 slug 再编辑。
  • 绑定与范围：Skill 按书绑定（启用状态不跨知识库共享），范围枚举 qa / research / both / ingest / all；问答与研究 Skill 只对当前书启用且范围匹配才注入，book-ingest 是编译的内置兜底，PPTX 任务有内置演示 Skill 兜底。
  • 预算与截断：Skill 区块总预算 8,000 字符、单个 6,000、配置 4,000，裁剪处标注「内容已截断」；最终运行 Prompt 才是实际生效内容的权威记录（并已被检查快照保存）。
  • 安全：Skill 只是 Markdown 指令，不能扩大工具权限、不可执行脚本；ZIP 导入限制文件数与大小，拒绝路径穿越、符号链接、二进制与脚本。
  • 发布流水线：候选版本须先通过固定评测套件的确定性文本契约检查（建库套件通过线 0.80，问答/研究/演示 0.75），再通过真实模型基准——当前版本与候选各一次聚合 Harness 调用、零工具、32 个固定样例（建库 12、问答 8、研究 6、演示 6），逐样例按指令遵循、安全、引用得分、引用有效性、非空输出五维评分，单样例总分 ≥0.75 且安全与引用维度全对才算通过；发布门槛还要求至少 80% 样例通过且相对基线回退不超过 0.03。回滚只接受历史 published 版本；基准 Run 的输出只进结果表，永不进知识变更集。

Token 用量统计

agent_runs 记录输入、输出、推理、缓存读写 token 与 usage_source。ACP 桥当前不转发供应商精确用量，问答与研究任务使用与 LLM 客户端一致的中英文启发式估算并如实标记 estimated；ACP UsageUpdate 只作为真实上下文占用展示。统计页按日期与归一化调用方（knowledge_qa / knowledge_task_*）聚合，只读已完成运行，并单列「未上报」——估算值不当作供应商账单。

08 / SECURITY

安全边界 — Agent 为什么越不了权

把前面各章的防线集中起来看，这套系统对「让 LLM 干活但不让它闯祸」的回答是一张纵深防御网：

防线机制
身份与范围能力令牌是 obw_ 前缀的 64 位十六进制高熵随机值，SQLite 只存 SHA-256，绑定 run_id + 知识库范围 + 工具白名单 + 过期时间（下限 300 秒，覆盖运行超时再加 60 秒收尾）；工具端从令牌读权限，忽略 Agent 试图扩大范围的参数
进程隔离每次 Run 独立 ACP 子进程 + 隔离临时工作区（原书不复制进可写区）；会话结束、取消或超时后连接与子进程组立即回收，无常驻池
权限升级Harness 的一切权限请求一律自动应答 Cancelled；每次 Run 恒叠加一份只读安全 patch，一次性禁用 Bash、PowerShell、文件系统、全盘搜索、Web、子代理、工作流、待办等 16 项 Harness 内建能力
密钥数据库只保存环境变量名或凭据库引用；密钥值只在后端进程环境中并以进程环境变量注入子进程，Provider Patch 落盘内容不含密钥；含能力令牌的 patch 文件权限收敛为 0600
网络出口唯一对外出口 book_fetch_external：仅显式授权的专题研究 Run 可见，HTTPS/443、域名精确边界、DNS 公网校验、禁重定向、原子预扣额度、文本 MIME、15 秒、512 KiB
写入Agent 只能提案；正式写入必须经人工审核 + 服务端复验 + 单事务；结构校验之上始终保留「事实正确性靠人」的诚实边界
参数所有工具 Schema additionalProperties: false，Rust 侧 deny_unknown_fields
数据边界每表携带 knowledge_base_id，复合唯一约束 + 跨库拒绝；检索工具范围来自令牌而非入参；MCP 网关 URL 由进程实际绑定端口推导并强制回环地址（非 127.0.0.1 / localhost / [::1] 直接拒绝），不硬编码
可追溯agent_runs + agent_run_events + agent_run_inspections 三件套：每次运行的 Prompt、Skill/配置快照、工具白名单、事件时间线与用量都不可变留痕
数据安全网Online Backup API 一致快照；迁移、删库、大变更集前自动备份；恢复要求输入 RESTORE、先验证完整性并自动生成 pre-restore 快照，失败自动回退

闭环的完整形状

Markdown 原书（只读）
  → 同步：source_documents / source_versions / source_spans + FTS5
  → 编译：检查点 + 指纹增量，ACP Run 分批炼化，严格 JSON 契约
  → 候选：knowledge_change_sets（proposed，附引用审计与级联影响）
  → 审核：人工批准 → 服务端复验 → 单事务写入 entries / claims / relations / citations
  → 消费：工作台浏览与体检 · 问答带 [S#] 引用 · 研究任务产报告与 PPTX
  → 回流：好回答与研究结论再次成为 proposed 候选，回到审核
  ↺ 原书更新 → 重新同步 → 指纹不变则只编译变化的来源

每一个箭头都有明确的表、工具与事务边界；每一次模型调用都有不可变快照；每一份进入正式库的知识都经过人的批准。这就是四个页面「形成一套完整流程」的全部含义——不是页面之间互相跳转，而是数据沿着一条可审计的单向管线流动，在每个关口被验证，在终点被人确认。

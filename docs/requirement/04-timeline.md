# 时间线模块 (Timeline) — 需求设计文档

> **文档编号**: REQ-04 | **版本**: v1.0 | **状态**: 设计中 | **最后更新**: 2026-05-29
>
> **上游依赖**: [顶层设计文档](../top_design.md) §5.2 时间线

---

## 1. 模块概述

### 1.1 定位

时间线模块为 ObsidianBrain 知识引擎提供 **知识演变的时间维度可视化** 能力。它从用户的 Obsidian 笔记库和本地代码仓库中自动采集各类时间事件，构建一条完整的知识活动时间线，帮助 LLM 回答诸如"上周我做了什么"、"这个主题的笔记是怎么演化的"、"去年今天我写了什么"等时间维度的问题。

### 1.2 核心价值

| 用户痛点 | 时间线模块的解决方式 |
|---|---|
| 知识管理缺乏时间视角 | 自动聚合多源时间事件，构建完整时间线 |
| 周报/月报手工整理耗时 | 结构化时间线数据直接作为周报数据源 |
| 知识演变过程不可见 | 按日分组的事件列表展示知识生长轨迹 |
| 缺少"回忆"触发机制 | "去年今日"功能为灵感熔炉提供历史素材 |

### 1.3 设计原则

- **被动采集为主**：事件采集在后台自动完成，不需要用户手动记录
- **多源融合**：融合笔记元数据、文件变更、Git 提交等多个维度的时间信号
- **结构化输出**：返回标准化的 JSON 结构，由 LLM 负责自然语言呈现
- **轻量存储**：仅存储事件摘要而非完整内容，控制数据库体积

## 2. 功能需求

### 2.1 数据收集 (Event Collection)

时间线模块从以下五种数据源自动采集时间事件：

#### 2.1.1 笔记 Frontmatter 日期提取

从 Obsidian 笔记的 YAML frontmatter 中提取日期字段，识别笔记的创建或重要标注时间。

**支持的日期字段**：
- `date` / `created` / `created_at` — 笔记创建时间
- `modified` / `updated` / `updated_at` / `lastmod` — 笔记最后修改时间
- `publish_date` / `published` — 发布日期（用于博客类笔记）

**支持的日期格式**：
- `2026-05-28` (ISO 8601 日期)
- `2026-05-28T14:30:00Z` (ISO 8601 完整时间)
- `2026-05-28 14:30:00` (带空格分隔)
- `2026/05/28` (斜杠分隔)
- `May 28, 2026` (英文月份)
- `28-05-2026` (日-月-年)

#### 2.1.2 文件名日期提取

从笔记文件名中正则匹配日期模式，适用于日记类、日志类笔记。

**支持的命名模式**：
- `2026-05-28-meeting.md` → 日期 2026-05-28
- `2026-05-28.md` (纯日期文件名)
- `20260528_daily.md` → 日期 2026-05-28
- `meeting-notes-20260528.md` → 日期 2026-05-28
- `2026/05/28/note.md` → 日期 2026-05-28 (目录层级日期)

#### 2.1.3 内容标签日期提取

扫描笔记正文中的特定格式标签，提取用户主动标注的时间事件。

**支持的标签格式**：
- `#date/2026-05-28` — 标注某事件发生于该日期
- `#date/2026-05-28/keyword` — 带关键词的日期标签

#### 2.1.4 文件监控事件收集

通过 `notify` crate 的文件系统监控，实时感知笔记的创建和修改事件，转化为时间线事件。

**采集的事件**：
- 文件创建 (`notify::EventKind::Create`)
- 文件内容修改 (`notify::EventKind::Modify`)
- 文件删除 (`notify::EventKind::Remove`) — 记录删除事件但不存储详情

#### 2.1.5 Git Commit 事件收集

从已注册的代码仓库（通过 `add_code_repo` 注册）中提取 Git 提交历史。

**采集的信息**：
- 提交哈希值（短哈希）
- 提交者
- 提交消息（首行摘要）
- 提交时间戳
- 涉及的仓库名称

### 2.2 事件类型定义

| 事件类型 | 枚举值 | 触发条件 | 典型来源 |
|---|---|---|---|
| 笔记创建 | `NoteCreated` | 检测到新笔记文件 | 文件监控、frontmatter `date`/`created` |
| 笔记修改 | `NoteModified` | 检测到笔记内容变更 | 文件监控、frontmatter `modified` |
| 代码提交 | `RepoCommit` | 检测到新的 Git 提交 | Git commit 历史扫描 |
| 雷达收藏 | `RadarSaved` | 用户将雷达文章保存到 vault | 雷达模块 `add_to_vault` 回调 |
| 记忆创建 | `MemoryCreated` | 新的记忆单元被创建 | 记忆模块 `add_memory` 回调 |

### 2.3 时间线查询

#### 2.3.1 工具定义

```
get_timeline(start_date: string, end_date: string, event_types?: string[], tags?: string[], limit?: int)
```

**参数说明**：

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `start_date` | string | 是 | — | 起始日期，格式 `YYYY-MM-DD` |
| `end_date` | string | 是 | — | 结束日期，格式 `YYYY-MM-DD` |
| `event_types` | string[] | 否 | 全部类型 | 过滤事件类型，如 `["note_created", "repo_commit"]` |
| `tags` | string[] | 否 | 不过滤 | 按标签过滤，匹配事件关联的任意标签 |
| `limit` | int | 否 | 200 | 最大返回事件数 |

### 2.4 统计摘要

在时间线查询结果中附带统计信息，同时在 `get_stats` 系统工具中也提供全局时间线统计：

**统计维度**：
- 指定时间段内的总事件数
- 按事件类型的分布计数
- 活跃天数（有事件发生的天数）
- 高频标签 Top 10
- 日均事件数
- 与上一同等时段的对比变化（如"本周比上周多 30% 的笔记活动"）

### 2.5 与其他模块的协作

#### 2.5.1 灵感熔炉 — "去年今日"素材

灵感熔炉的概念组合模式 (`concept_combo`) 可以向时间线模块请求"去年今日"（On This Day）的笔记作为创意素材。

**交互接口**：
```
get_on_this_day(years_ago: int) -> Vec<TimelineEvent>
```

返回 N 年前同一日期的事件列表，供灵感熔炉挑选作为跨界组合的输入。

#### 2.5.2 周报生成 — 数据源

`weekly_review` 技能调用时间线模块获取本周事件，聚合后交给 LLM 生成结构化周报：

**数据流**：
```
weekly_review 技能
    → get_timeline(本周一, 今天)
    → 统计聚合
    → LLM 生成周报摘要
    → 写入 vault（可选）
```

#### 2.5.3 智识雷达 — 兴趣漂移参考

时间线事件（特别是高频标签变化趋势）作为智识雷达判断用户兴趣漂移的参考信号之一：

**提供的信号**：
- 最近 30 天标签频率变化
- 新增主题领域（首次出现的标签）
- 活跃度下降的主题

## 3. 用户故事

### US-01: 每日回顾

**角色**：个人知识工作者
**场景**：每天结束时，用户想了解今天在知识管理方面做了什么
**触发**：用户对 LLM 说"帮我回顾一下今天做了什么"
**期望流程**：
1. LLM 调用 `get_timeline(start_date: "2026-05-29", end_date: "2026-05-29")`
2. 引擎返回今日所有事件，按时间排序
3. LLM 基于结构化数据生成自然语言回顾：
   - "今天你新增了一篇关于 Rust 异步编程的笔记，修改了 2 次"
   - "在 my-app 项目中提交了 3 次代码，主要涉及认证模块"
   - "保存了一篇关于 RAG 的雷达文章"
**验收标准**：
- 返回结果包含今日所有事件类型
- 事件按时间倒序排列
- 包含每条事件的标签和关联路径

### US-02: 周报自动生成

**角色**：个人知识工作者
**场景**：周末用户想生成一份本周的知识活动周报
**触发**：用户对 LLM 说"帮我生成本周周报"或调用 `weekly_review` 技能
**期望流程**：
1. LLM 调用 `get_timeline(start_date: "2026-05-25", end_date: "2026-05-31")`
2. 引擎返回本周所有事件及统计摘要
3. LLM 基于统计数据生成周报：
   - 本周概览：新增 5 篇笔记，修改 12 次，代码提交 8 次
   - 重点主题：Rust 异步编程（3 篇笔记）、AI RAG 技术（2 篇笔记）
   - 代码活动：my-app 项目主要进展在认证模块
   - 与上周对比：笔记活动增加 20%，代码活动持平
**验收标准**：
- 统计数据准确（事件计数、活跃天数、高频标签）
- 覆盖所有事件类型
- 支持自定义日期范围

### US-03: 知识演变追踪

**角色**：研究者/技术写作者
**场景**：用户想了解某个主题的笔记是如何随时间演变的
**触发**：用户对 LLM 说"我的 Rust 笔记是怎么演变的"
**期望流程**：
1. LLM 调用 `get_timeline(start_date: "2026-01-01", end_date: "2026-05-29", tags: ["rust"])`
2. 引擎返回所有与 Rust 相关的时间线事件
3. LLM 分析演变趋势：
   - "1 月你主要关注 Rust 基础语法，写了 4 篇入门笔记"
   - "3 月开始深入异步编程，tokio 相关笔记增加了 6 篇"
   - "5 月转向实战项目，代码提交频率明显增加"
**验收标准**：
- 标签过滤正确生效
- 事件按时间正序排列，展示演变过程
- 长时段查询不超时（< 2s 响应）

### US-04: 去年今日回忆

**角色**：个人知识工作者
**场景**：用户想要获得灵感，通过回顾过去的笔记触发新想法
**触发**：用户对 LLM 说"去年今天我写了什么"或灵感熔炉主动请求
**期望流程**：
1. LLM 调用 `get_timeline(start_date: "2025-05-29", end_date: "2025-05-29")`
2. 引擎返回去年今日的事件
3. LLM 展示回忆内容并关联当前兴趣：
   - "去年的今天你写了一篇关于睡眠实验的笔记"
   - "这篇笔记和你最近关注的'认知负荷管理'主题有关联"
   - "要不要重新看看，也许能产生新的想法？"
**验收标准**：
- 精确匹配历史日期
- 无数据时优雅提示"去年今日没有记录"
- 返回的事件包含完整路径以便跳转

### US-05: 项目进度回顾

**角色**：开发者
**场景**：用户想了解某个代码仓库在一段时间内的开发进展
**触发**：用户对 LLM 说"my-app 项目上个月进展如何"
**期望流程**：
1. LLM 调用 `get_timeline(start_date: "2026-04-01", end_date: "2026-04-30", event_types: ["repo_commit"])`
2. 引擎返回该项目当月的所有提交事件
3. LLM 基于提交消息总结项目进展：
   - "4 月 my-app 共提交 23 次"
   - "主要工作：月初完成数据库迁移模块，月中实现 API 鉴权，月底进行性能优化"
   - "4 月 15 日有一次重要的架构重构提交"
**验收标准**：
- 事件类型过滤正确
- 提交消息完整保留
- 支持按仓库名过滤（通过标签或扩展参数）

### US-06: 月度知识盘点

**角色**：知识工作者
**场景**：月末用户想盘点本月的知识输入和输出情况
**触发**：用户对 LLM 说"帮我做个本月知识盘点"
**期望流程**：
1. LLM 调用 `get_timeline(start_date: "2026-05-01", end_date: "2026-05-31")`
2. 引擎返回完整月度事件及详细统计
3. LLM 生成盘点报告：
   - 输入维度：保存了 8 篇雷达文章，阅读了 3 篇论文笔记
   - 输出维度：新增 12 篇原创笔记，修改 34 次
   - 代码维度：3 个仓库共 45 次提交
   - 知识热点：Rust 异步编程、RAG 技术、认知科学
   - 活跃度曲线：月初和月末活跃度较高，月中偏低
**验收标准**：
- 统计数据多维度且准确
- 支持月度级别的日期范围查询
- 标签趋势统计正确

### US-07: 断档检测与恢复

**角色**：追求连续记录的知识工作者
**场景**：用户想知道自己有多久没写笔记了，或者哪些领域"断档"了
**触发**：用户对 LLM 说"我最近有几天没写笔记了"
**期望流程**：
1. LLM 调用 `get_timeline(start_date: "2026-05-01", end_date: "2026-05-29")`
2. 引擎返回每日事件分布
3. LLM 分析活跃间隔：
   - "你最近一次创建笔记是 5 月 25 日，距今 4 天"
   - "本月有 3 个连续 3 天以上的空窗期：5月3日-6日、5月12日-15日"
   - "'ai' 标签的笔记已经 15 天没有更新了"
**验收标准**：
- 能正确识别无事件日期
- 统计信息中包含活跃天数供 LLM 分析
- 长时段查询性能稳定

### US-08: 跨模块协作 — 雷达兴趣漂移

**角色**：智识雷达模块
**场景**：雷达模块需要判断用户近期兴趣变化以调整推荐策略
**触发**：雷达定时任务内部调用时间线模块
**期望流程**：
1. 雷达模块请求最近 30 天的标签频率统计
2. 时间线模块返回标签趋势数据
3. 雷达模块据此调整用户兴趣向量的权重：
   - 上升趋势标签权重增加
   - 下降趋势标签权重衰减
   - 新出现的标签额外加权
**验收标准**：
- 提供按标签聚合的频率统计 API
- 响应时间 < 100ms（内部调用，不含 LLM）

## 4. 非功能需求

### 4.1 查询性能

| 查询场景 | 目标延迟 | 事件规模 |
|---|---|---|
| 单日查询 | < 50ms | ~50 条事件 |
| 一周查询 | < 100ms | ~300 条事件 |
| 一月查询 | < 300ms | ~1500 条事件 |
| 全年查询 | < 2000ms | ~15000 条事件 |

### 4.2 事件保留策略

| 事件类型 | 保留期限 | 过期处理 |
|---|---|---|
| `NoteCreated` | 永久保留 | — |
| `NoteModified` | 保留最近 2 年 | 超过 2 年的按月聚合为摘要记录 |
| `RepoCommit` | 保留最近 1 年 | 超过 1 年的按月聚合 |
| `RadarSaved` | 永久保留 | — |
| `MemoryCreated` | 保留最近 1 年 | 超过 1 年的按月聚合 |

**聚合策略**：过期事件不是直接删除，而是按月压缩为一条摘要事件（如"2025年1月：新增 15 篇笔记，修改 42 次"），保留在 `timeline_monthly_summaries` 表中。

### 4.3 数据一致性

- 事件写入采用 SQLite 事务保证原子性
- 文件监控事件在采集后 500ms 内完成写入
- 历史扫描（如首次启动时的全量 frontmatter 扫描）采用批量写入，每批 100 条

### 4.4 资源占用

- 事件存储体积：单条事件约 500 bytes，10000 条事件约 5MB
- 内存占用：查询时不超过 10MB 额外内存
- 后台采集 CPU 占用 < 5%（单核）

## 5. 事件数据模型

### 5.1 TimelineEvent（时间线事件）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | UUID | 是 | 事件唯一标识 |
| `date` | Date | 是 | 事件发生日期 (YYYY-MM-DD) |
| `timestamp` | DateTime | 否 | 精确时间戳（部分事件仅有日期） |
| `event_type` | EventType | 是 | 事件类型枚举 |
| `title` | String | 是 | 事件标题（简短，不超过 100 字符） |
| `summary` | String | 否 | 事件摘要（不超过 500 字符） |
| `tags` | Vec\<String\> | 否 | 关联标签列表 |
| `related_paths` | Vec\<PathBuf\> | 否 | 关联的文件路径列表 |
| `source` | String | 是 | 事件来源标识（"frontmatter"/"filename"/"filewatcher"/"git"/"radar"/"memory"） |
| `metadata` | JSON | 否 | 扩展元数据（如 Git commit hash、仓库名等） |

### 5.2 EventType（事件类型枚举）

| 值 | 字符串表示 | 说明 |
|---|---|---|
| `NoteCreated` | `note_created` | 笔记创建 |
| `NoteModified` | `note_modified` | 笔记修改 |
| `RepoCommit` | `repo_commit` | 代码仓库提交 |
| `RadarSaved` | `radar_saved` | 雷达文章保存 |
| `MemoryCreated` | `memory_created` | 记忆单元创建 |

### 5.3 DailyEvents（按日分组）

| 字段 | 类型 | 说明 |
|---|---|---|
| `date` | Date | 日期 |
| `event_count` | usize | 当日事件数 |

## 6. 与其他模块的接口约定

### 6.1 事件写入接口（其他模块 → 时间线）

其他模块在特定操作完成后，通过内部事件总线向时间线模块发送事件：

| 调用方 | 触发操作 | 发送的事件类型 | 事件内容 |
|---|---|---|---|
| 记忆模块 | `add_memory` 成功 | `MemoryCreated` | 记忆标题、来源笔记路径、标签 |
| 雷达模块 | `add_to_vault` 成功 | `RadarSaved` | 文章标题、来源、保存路径 |
| 文件监控 | 文件创建/修改 | `NoteCreated`/`NoteModified` | 文件路径、变更类型 |
| Git 扫描 | 定时扫描提交 | `RepoCommit` | 仓库名、提交信息、时间戳 |

### 6.2 事件查询接口（时间线 → 其他模块）

| 调用方 | 调用场景 | 查询参数 | 期望返回 |
|---|---|---|---|
| 灵感熔炉 | "去年今日"素材 | 精确日期 + 仅笔记类型 | 当日笔记事件列表 |
| 周报技能 | 周报数据源 | 本周日期范围 | 完整事件 + 统计 |
| 雷达模块 | 兴趣漂移分析 | 最近 30 天 + 标签聚合 | 标签频率趋势 |
| LLM 工具 | 用户直接查询 | 用户指定参数 | 完整时间线响应 |

### 6.3 事件总线协议

时间线模块通过系统内部的 EventBus 订阅和发布事件：

```
// 订阅的事件
EventBus::subscribe("note.created")
EventBus::subscribe("note.modified")
EventBus::subscribe("memory.created")
EventBus::subscribe("radar.saved")
EventBus::subscribe("repo.commit_detected")

// 发布的事件（供其他模块消费）
EventBus::publish("timeline.event_recorded", event)
EventBus::publish("timeline.daily_summary_ready", daily_summary)
```

## 7. 约束与假设

### 7.1 约束

1. **本地运行**：所有数据采集和存储均在本地完成，不依赖外部服务（LLM 摘要生成除外）
2. **SQLite 单线程写入**：SQLite 的写入操作需通过连接池排队，高并发写入场景需要控制速率
3. **文件系统依赖**：frontmatter 和文件名日期提取依赖文件系统的可用性
4. **Git 仓库预注册**：仅采集通过 `add_code_repo` 注册的仓库的 commit 历史
5. **日期精度**：部分事件仅有日期而无精确时间戳（如 frontmatter 日期），此类事件的 timestamp 字段为 null

### 7.2 假设

1. 用户的 Obsidian vault 路径已在配置文件中正确设置
2. 笔记使用标准 Markdown + YAML frontmatter 格式
3. Git 仓库可通过 git2 (libgit2) 正常访问
4. 文件系统监控 (notify) 能在目标操作系统上正常工作（macOS 使用 FSEvents，Linux 使用 inotify）
5. 事件数量在合理范围内：每日不超过 500 条事件，每年不超过 50000 条
6. 用户对"去年今日"等功能有合理的期望（1 年前可能尚无使用记录）

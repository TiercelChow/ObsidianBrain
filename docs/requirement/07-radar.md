## 1. 模块概述

### 1.1 定位

智识雷达是 ObsidianBrain 的 **外部信息感知模块**。与传统的 RSS 阅读器或信息聚合工具不同，智识雷达的核心理念是：

> **让外部信息来找你的笔记，而不是你去搜索。**

它基于用户已有的 **个人知识图谱**（Obsidian vault 中的笔记标签、关键词、访问频率等），构建用户的 **兴趣画像**，然后从外部信息源（RSS/Atom、arXiv、HackerNews、Reddit 等）中自动抓取新内容，通过 **标签匹配和关键词相关性计算** 进行 **个性化相关性排序**，将最有价值的信息主动推送到用户面前。

### 1.2 核心价值

| 痛点 | 智识雷达的解决方式 |
|---|---|
| 信息过载，每天有大量文章/论文/帖子需要手动筛选 | 基于个人知识图谱自动过滤，只展示高相关性内容 |
| RSS 阅读器订阅越来越多，阅读压力巨大 | 用标签和关键词匹配替代人工筛选，自动降权低相关内容 |
| 收藏了等于学了——大量文章收藏后从未阅读 | 一键纳藏到 vault，自动摘要 + 记忆索引，真正融入知识体系 |
| 外部信息与已有笔记割裂 | 自动关联已有笔记，形成知识闭环 |
| 不知道自己的知识盲区在哪里 | 通过推荐内容发现与自己领域相关但尚未涉猎的方向 |

### 1.3 与其他模块的关系

智识雷达是 ObsidianBrain 五大核心模块之一（参见[顶层设计文档 §5.5](../top_design.md)），与记忆引擎、时间线、灵感熔炉、代码仓 Hub 存在数据交互：

- **记忆引擎**：提供笔记标签和关键词用于构建用户兴趣画像；纳藏文章后通过 Obsidian API 自动可搜索
- **时间线**：记录文章保存（RadarSaved）事件
- **灵感熔炉**：雷达抓取的外部内容可作为灵感碰撞的素材
- **代码仓 Hub**：技术类文章可与代码仓库产生关联

## 2. 功能需求

### 2.1 外部源管理

#### 2.1.1 支持的源类型

| 源类型 | 协议/接口 | 说明 |
|---|---|---|
| RSS/Atom | 标准 RSS 2.0 / Atom 协议 | 支持任意 RSS/Atom feed URL，包括博客、新闻、技术周刊等 |
| arXiv | arXiv API (OAI-PMH) | 按学科分类 (cs.AI, cs.CL 等) 和关键词查询论文 |
| HackerNews | Algolia HN Search API | 按分数、评论数过滤，支持关键词过滤 |
| Reddit | Reddit JSON API (公开端点) | 按 subreddit 订阅，按 upvotes 过滤 |

#### 2.1.2 源配置

所有外部源通过 `config/radar_sources.toml` 配置文件定义，格式参见开发设计文档。配置项包括：

- 源名称 (`name`)：唯一标识符
- 源类型 (`type`)：`rss` / `arxiv` / `hackernews` / `reddit`
- 启用状态 (`enabled`)：是否参与定时拉取
- 类型特定参数：如 RSS 的 feed URL 列表、arXiv 的学科分类、HN 的分数阈值、Reddit 的 subreddit 列表
- 通用参数：每次最大拉取条数 (`max_items`)、可信度权重 (`trust_weight`)

#### 2.1.3 源 CRUD 操作

- **添加源**：通过 LLM 工具调用 `add_radar_source(type, name, config)` 动态添加新的信息源
- **删除源**：通过 LLM 工具调用 `remove_radar_source(name)` 移除已有源
- **启用/禁用源**：通过 LLM 工具调用 `toggle_radar_source(name, enabled)` 控制源的启用状态
- **列出源**：通过 LLM 工具调用 `list_radar_sources()` 查看所有已配置源及其状态

#### 2.1.4 定时拉取

- 默认拉取频率：**每 6 小时**（可通过 `config/default.toml` 的 `radar.fetch_interval_hours` 配置）
- 支持自定义 cron 表达式（高级用户）
- 拉取过程在后台异步执行，不阻塞主服务和工具调用
- 每个源独立拉取，单个源失败不影响其他源
- 拉取结果缓存在 SQLite `radar_items` 表中，避免重复拉取

### 2.2 个性化相关性排序

#### 2.2.1 用户兴趣画像构建

基于用户最近 30 天的活跃笔记构建 **兴趣画像**，作为个性化推荐的基准：

- **活跃笔记定义**：最近 30 天内有创建、修改或访问记录的笔记
- **权重计算**：
  - 时间衰减因子：越近的笔记权重越高（指数衰减）
  - 访问频次因子：`access_count` 越高的笔记权重越大
  - 重要度因子：`importance` 评分高的笔记权重更大
- **画像合成**：
  - 提取所有活跃笔记的 frontmatter 标签（tags），按权重聚合，得到用户 **标签偏好列表**
  - 提取活跃笔记标题和正文中的高频关键词，得到用户 **关键词偏好列表**
- **更新策略**：每次拉取新内容前重新计算（或缓存 24 小时内的计算结果）

#### 2.2.2 文章相关性计算

对每篇新抓取的文章：

1. 提取标题 + 摘要文本
2. 从标题和摘要中提取关键词和主题标签
3. 计算文章关键词/标签与用户兴趣画像的 **匹配度**：
   - **标签匹配度**：文章标签与用户标签偏好列表的交集权重
   - **关键词匹配度**：文章关键词与用户关键词偏好列表的匹配程度
   - 综合两者得到最终相关性得分

#### 2.2.3 过滤规则

文章必须同时满足以下条件才会进入推荐列表：

- 相关性得分 > 阈值（默认 `0.3`，可配置）
- 不在 **已读列表** 中（状态不为 `Read` 或 `Saved`）
- 不在 **已忽略列表** 中（状态不为 `Dismissed`）
- URL 不在全局去重表中

#### 2.2.4 多因子排序

通过过滤的文章按以下公式综合排序：

```
最终得分 = α × 标签关键词匹配度 + β × 来源可信度 + γ × 时效性 - δ × 内容重复度
```

- **标签关键词匹配度** (α=0.6)：文章标签和关键词与用户兴趣画像的匹配程度
- **来源可信度** (β=0.15)：每个源有一个可信度权重（可在配置中设定）
- **时效性** (γ=0.15)：越新的文章得分越高，按发布时间线性衰减
- **内容重复度** (δ=0.1)：与已有笔记内容越相似（基于标题和关键词重叠），降权越多（避免推荐已经知道的内容）

#### 2.2.5 去重策略

- **URL 去重**：同一 URL 的文章只保留一条记录
- **内容相似度去重**：计算新文章与已有笔记的标题和关键词重叠度，重叠度 > 0.8 的文章降权处理（降低 50% 得分）
- **标题去重**：标题编辑距离 < 3 的文章视为同一篇

### 2.3 信息展示

#### 2.3.1 get_radar 工具

提供 `get_radar(limit?, query?)` 工具供 LLM 调用：

**参数**：

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `limit` | integer | 否 | 10 | 返回条目数量上限 |
| `query` | string | 否 | null | 可选的查询关键词，用于在当前雷达结果中进一步筛选 |

**返回字段**：

每篇雷达条目包含以下信息：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string (UUID) | 条目唯一标识 |
| `title` | string | 文章标题 |
| `summary` | string | 文章摘要（优先使用源提供的摘要，否则取正文前 200 字） |
| `source` | string | 来源标识（如 `"arxiv"`, `"hackernews"`, `"rss:tech-rss"`） |
| `url` | string | 文章原始链接 |
| `relevance_score` | float | 相关性得分 (0-1) |
| `related_notes` | string[] | 关联的已有笔记路径列表（最多 3 篇） |
| `published_at` | string (ISO 8601) | 文章发布时间 |
| `status` | string | 当前状态 (`New` / `Read` / `Saved` / `Dismissed`) |

**行为**：
- 调用 `get_radar` 会将返回条目的状态从 `New` 更新为 `Read`
- 如果提供 `query` 参数，会在结果中按关键词进一步过滤
- 结果按最终得分降序排列

### 2.4 一键纳藏

#### 2.4.1 add_to_vault 工具

提供 `add_to_vault(article_id, target_dir?)` 工具将感兴趣的文章保存到 Obsidian vault：

**参数**：

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `article_id` | string (UUID) | 是 | — | 要保存的文章 ID |
| `target_dir` | string | 否 | `"radar/"` | vault 中保存的目标目录 |

**纳藏流程**：

1. **正文提取**：使用 readability 算法从原始网页提取正文内容，去除广告、导航栏等噪声
2. **生成 Obsidian 笔记**：按模板生成 Markdown 文件，包含：
   - YAML frontmatter：来源、URL、保存日期、自动标签、相关性得分
   - 正文内容：提取后的文章正文
   - LLM 生成的中文摘要
   - 关联笔记的双向链接
3. **写入 vault**：以 `YYYY-MM-DD-<slugified-title>.md` 格式命名，通过 Obsidian API 写入指定目录
4. **自动可搜索**：新笔记写入后由 Obsidian 自动维护搜索索引，可通过 Obsidian API 搜索
5. **更新时间线**：记录 RadarSaved 事件到时间线
6. **更新状态**：将文章状态更新为 `Saved`

**返回**：保存后的笔记路径、Obsidian URI、自动摘要

### 2.5 忽略操作

#### 2.5.1 dismiss_radar_item 工具

提供 `dismiss_radar_item(article_id)` 工具标记不感兴趣的文章：

- 将文章状态更新为 `Dismissed`
- 被忽略的文章不会再出现在 `get_radar` 结果中
- 忽略记录长期保留，用于未来优化推荐质量（作为负样本）

### 2.6 状态管理

每个雷达条目有四个状态，状态流转如下：

```
            ┌──────────────┐
            │     New       │  ← 新抓取且通过过滤的文章
            └──────┬───────┘
                   │
         ┌─────────┼─────────┐
         │         │         │
         ▼         ▼         ▼
  ┌──────────┐ ┌────────┐ ┌──────────┐
  │   Read   │ │ Saved  │ │ Dismissed│
  │ (已查看) │ │(已纳藏)│ │ (已忽略) │
  └────┬─────┘ └────────┘ └──────────┘
       │
       ├─────────┐
       │         │
       ▼         ▼
  ┌────────┐ ┌──────────┐
  │ Saved  │ │ Dismissed│
  └────────┘ └──────────┘
```

**状态说明**：

| 状态 | 含义 | 出现在 get_radar 结果中 |
|---|---|---|
| `New` | 新抓取、未查看 | ✅ 是 |
| `Read` | 已通过 get_radar 查看但未操作 | ❌ 否 |
| `Saved` | 已纳藏到 vault | ❌ 否 |
| `Dismissed` | 已标记忽略 | ❌ 否 |

## 3. 用户故事

### US-01：早晨知识播报

**角色**：日常使用 ObsidianBrain 的开发者
**场景**：用户早上打开 Claude 对话，想了解昨晚到现在有什么与自己关注领域相关的新内容。

**对话**：
> 用户："有什么新东西值得看？"
> LLM 调用 `get_radar(limit: 5)`
> LLM 回复："根据你的知识库，以下是今天最值得关注的 5 篇内容：
> 1. 📄 《RAG 系统的最新进展综述》(arXiv, 相关度 0.92) — 与你的 ai/rag-notes.md 高度相关
> 2. 🔥 《Rust 异步运行时的性能对比》(HackerNews, 相关度 0.88) — 与你的 programming/rust-async.md 相关
> 3. ..."

**验收**：返回结果按相关性排序，每篇都标注关联的已有笔记。

### US-02：论文追踪

**角色**：跟踪 NLP 领域进展的研究者
**场景**：用户配置了 arXiv 的 cs.CL 和 cs.AI 分类源，希望每天自动获取最新论文。

**操作**：
1. 用户在 `radar_sources.toml` 中配置 arXiv 源
2. 系统每 6 小时自动拉取新论文
3. 根据用户兴趣画像（基于已有的 NLP 笔记标签和关键词）筛选高相关性论文
4. 用户通过 `get_radar` 查看推荐论文列表
5. 对感兴趣的论文使用 `add_to_vault` 保存

**验收**：arXiv 论文正确抓取，分类过滤有效，相关性排序准确。

### US-03：一键收藏深度文章

**角色**：在 HackerNews 上发现一篇深度技术博客
**场景**：用户通过雷达看到一篇很长的技术文章，不想现在读但想保存以后看。

**对话**：
> 用户："把第 3 篇保存下来"
> LLM 调用 `add_to_vault(article_id: "radar-xxxx")`
> LLM 回复："已保存到 radar/2026-05-29-building-a-search-engine-from-scratch.md。
> 自动摘要：本文详细介绍了从零构建搜索引擎的核心步骤，包括倒排索引、BM25 排序...
> 已自动关联到你的笔记：cs/search-engine.md, cs/information-retrieval.md"

**验收**：
- 文件正确写入 vault 的 `radar/` 目录
- frontmatter 包含来源、URL、日期、标签
- 正文已通过 readability 提取，格式干净
- 记忆系统已索引新笔记
- 时间线记录了保存事件

### US-04：忽略不感兴趣的内容

**角色**：信息筛选用户
**场景**：雷达推荐了一篇标题相关但内容质量低的文章，用户想忽略它。

**对话**：
> 用户："第 2 篇不感兴趣，忽略掉"
> LLM 调用 `dismiss_radar_item(article_id: "radar-yyyy")`
> LLM 回复："已忽略。这类内容以后会降低推荐权重。"

**验收**：文章状态变为 Dismissed，不再出现在后续推荐中。

### US-05：动态添加新的信息源

**角色**：想要扩展信息来源的用户
**场景**：用户听说了一个很好的技术博客，想把它加到雷达监控中。

**对话**：
> 用户："帮我加一个 RSS 源，Simon Willison 的博客"
> LLM 调用 `add_radar_source(type: "rss", name: "simonwillison", config: { feeds: ["https://simonwillison.net/atom/everything/"] })`
> LLM 回复："已添加 RSS 源 'simonwillison'，将在下次拉取时生效。"

**验收**：源添加到 `radar_sources.toml`，下次定时拉取时包含该源。

### US-06：按主题筛选雷达结果

**角色**：临时关注某个特定话题的用户
**场景**：用户最近在研究 WASM 相关内容，想看看雷达里有没有相关文章。

**对话**：
> 用户："雷达里有没有 WebAssembly 相关的内容？"
> LLM 调用 `get_radar(limit: 5, query: "WebAssembly WASM")`
> LLM 回复："找到 2 篇相关内容：
> 1. 《WASM 在边缘计算中的实践》(相关度 0.85)
> 2. 《从 JavaScript 迁移到 WASM 的经验总结》(相关度 0.78)"

**验收**：query 参数有效过滤并重新排序结果。

### US-07：禁用暂时不关注的源

**角色**：需要管理信息流量的用户
**场景**：用户最近在赶项目，暂时不想看 Reddit 的内容。

**对话**：
> 用户："先把 Reddit 源暂停"
> LLM 调用 `toggle_radar_source(name: "reddit-programming", enabled: false)`
> LLM 回复："已禁用 Reddit 源 'reddit-programming'。需要时可以随时重新启用。"

**验收**：Reddit 源状态变为 disabled，定时拉取时跳过该源。

### US-08：查看雷达源状态

**角色**：想确认信息源配置的用户
**场景**：用户想知道当前配置了哪些信息源，运行状态如何。

**对话**：
> 用户："看看我的雷达源配置"
> LLM 调用 `list_radar_sources()`
> LLM 回复："当前配置了 4 个信息源：
> - ✅ hackernews (HN) — 已启用，最后拉取: 2小时前，累计抓取: 45 篇
> - ✅ arxiv-cs (arXiv) — 已启用，最后拉取: 2小时前，累计抓取: 28 篇
> - ✅ tech-rss (RSS) — 已启用，最后拉取: 2小时前，累计抓取: 67 篇
> - ❌ reddit-programming (Reddit) — 已禁用"

**验收**：返回所有源的完整状态信息。

### US-09：回顾纳藏历史

**角色**：想回顾之前保存过哪些文章的用户
**场景**：用户通过时间线查看之前纳藏的文章。

**对话**：
> 用户："这个月保存了哪些文章？"
> LLM 先调用 `get_timeline(start_date: "2026-05-01", end_date: "2026-05-29")`
> 然后过滤出 RadarSaved 类型事件
> LLM 回复："本月共保存了 8 篇文章：
> - 5月28日: 《RAG 系统优化实践》→ radar/2026-05-28-rag-optimization.md
> - 5月25日: 《Rust 所有权模型深入解析》→ radar/2026-05-25-rust-ownership.md
> - ..."

**验收**：时间线正确记录 RadarSaved 事件，可通过时间线查询。

### US-10：批量管理雷达结果

**角色**：积累了大量未读雷达条目的用户
**场景**：用户出差一周回来，雷达积累了很多条目，想快速处理。

**对话**：
> 用户："看看这周的雷达，只给我看最相关的 3 篇，其他的都忽略掉"
> LLM 调用 `get_radar(limit: 20)` 获取全部结果
> 展示 top 3 给用户
> 对其余 17 篇批量调用 `dismiss_radar_item`
> LLM 回复："已为你展示最相关的 3 篇，其余 17 篇已标记忽略。"

**验收**：批量操作正确执行，状态全部更新。

## 4. 非功能需求

### 4.1 拉取频率与性能

| 指标 | 要求 | 说明 |
|---|---|---|
| 定时拉取间隔 | 默认 6 小时，可配置 1-24 小时 | 通过 `radar.fetch_interval_hours` 配置 |
| 单次拉取耗时 | < 5 分钟（所有源合计） | 各源并行拉取，单个源超时 30 秒 |
| 相关性排序耗时 | < 5 秒（100 篇文章） | 标签和关键词匹配计算 |
| 单源最大条目数 | 默认 20 条/次，可配置 | 防止单次拉取过多数据 |
| 总存储上限 | 最多保留 1000 条雷达条目 | 超出的旧条目自动清理（保留 Saved 状态的） |

### 4.2 存储约束

| 存储项 | 上限 | 清理策略 |
|---|---|---|
| SQLite `radar_items` 表 | 1000 条 | FIFO 清理 New/Read 状态的最旧条目 |
| 纳藏的笔记文件 | 无上限 | 用户自行管理 vault 中的文件 |
| 源配置文件 | 无硬上限 | 建议不超过 50 个源 |

### 4.3 推荐准确性

| 指标 | 目标 | 衡量方式 |
|---|---|---|
| 相关性阈值默认值 | 0.3 | 标签关键词匹配度阈值 |
| 推荐准确率 | > 70% 的推荐条目被用户查看 | 通过 Read 状态占比衡量 |
| 纳藏率 | > 20% 的查看条目被保存 | 通过 Saved / Read 比率衡量 |
| 误忽略率 | < 10% | 被忽略的条目中不应有过多高相关性内容 |

### 4.4 可靠性

- 单个源拉取失败不影响其他源
- 拉取过程中网络中断时，已成功的条目正常入库，失败的源在下次拉取时重试
- 服务重启后，定时任务自动恢复，不丢失已抓取的条目

### 4.5 隐私

- 外部源拉取仅发送必要的 API 请求（查询参数），不附带任何用户个人数据
- 纳藏操作仅通过 Obsidian API 在本地 vault 写入，不涉及外部传输

## 6. 约束与假设

### 6.1 约束

1. **网络依赖**：外部源拉取需要网络连接。在离线环境下，雷达仅提供已缓存的条目查询和纳藏操作，无法拉取新内容。
2. **API 限流**：各外部 API 有调用频率限制（arXiv: 3秒/请求, Reddit: 60次/分钟, HN: 无明确限制但需礼貌使用），需要合理控制拉取频率。
3. **内容质量不可控**：外部源的内容质量参差不齐，系统只能通过标签和关键词匹配进行过滤，无法保证所有推荐内容都是高质量的。
4. **Readability 提取限制**：部分网站（SPA、需要 JS 渲染的页面）可能无法正确提取正文，降级为仅保存摘要。

### 6.2 假设

1. 用户的 Obsidian vault 中有足够多的笔记（≥10 篇）来构建有意义的用户兴趣画像。笔记过少时降级为按热度和时效性排序。
2. 用户的网络环境能正常访问配置的外部源（部分源可能需要代理）。
3. arXiv API、HackerNews API、Reddit API 的公开端点在可预见的未来保持可用。
4. 用户接受定时后台拉取的网络流量消耗（每次拉取预计 < 5MB）。
5. 文章的正文内容可以通过 readability 算法有效提取（覆盖 > 80% 的文章）。

## 7. 验收标准

### 7.1 功能验收

| 编号 | 验收项 | 通过条件 |
|---|---|---|
| AC-01 | 源配置加载 | 系统启动时正确解析 `radar_sources.toml`，加载所有配置的源 |
| AC-02 | 定时拉取 | 按配置的间隔定时拉取，每次拉取结果正确存入 SQLite |
| AC-03 | 增量拉取 | 已拉取过的文章不重复入库（URL 去重） |
| AC-04 | 兴趣画像构建 | 基于最近 30 天活跃笔记正确提取标签偏好和关键词偏好 |

| AC-11 | 源 CRUD | 通过工具正确添加/删除/启用/禁用源，配置持久化 |

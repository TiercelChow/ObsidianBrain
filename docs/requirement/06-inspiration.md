# 需求设计文档：灵感熔炉 (Inspiration Forge)

> **模块编号**: 06 | **版本**: v0.1 | **状态**: 设计中 | **最后更新**: 2026-05-29
>
> **上游文档**: [顶层设计文档 (top_design.md)](../top_design.md) §5.4

---

## 1. 模块概述

### 1.1 定位

灵感熔炉是 ObsidianBrain 中唯一**主动制造知识碰撞**的模块。它不同于传统的"随机笔记"功能——后者只是随机打开一篇笔记，而灵感熔炉**有意地选取两个距离较远的概念**，迫使 LLM 在用户的知识库中找到出人意料的关联。

### 1.2 核心理念

> "创新就是旧元素的新组合。" —— 乔布斯

灵感熔炉的原料完全来自用户自己的笔记和代码库：

- **笔记侧**：用户积累的知识、想法、读书笔记、实验记录
- **代码侧**：用户正在开发的项目、使用的技术栈、解决问题的方案

通过**跨界组合**、**反向提问**、**对立观点**三种模式，从不同角度刺激用户产生新的思考方向。

### 1.3 与现有方案的区别

| 功能 | 传统方案 | 灵感熔炉 |
|---|---|---|
| 随机笔记 | 随机打开一篇笔记 | 基于概念距离有意选取"远距"概念组合 |
| 每日回顾 | 展示今日修改的笔记 | 对笔记内容提出用户未想过的问题 |
| 知识图谱 | 展示标签/链接关系 | 故意跨越知识边界制造碰撞 |
| AI 头脑风暴 | 依赖通用知识库 | 完全基于用户个人知识生成 |

### 1.4 在系统中的角色

在 [top_design.md](../top_design.md) 的架构中，灵感熔炉作为核心服务层的一个 Service 存在（`Inspiration Service`），对外通过 `get_inspiration` 工具暴露给 LLM 调用。

```
LLM 调用 get_inspiration(type, note_path?)
    │
    ▼
Inspiration Service
    ├── 从记忆引擎获取标签/关键词
    ├── 从时间线获取近期素材
    ├── 从代码仓获取技术概念
    │
    ▼
LLM Client 生成创意
    │
    ▼
结构化结果 + Obsidian 链接
```

## 2. 功能需求

### 2.1 随机概念组合（concept_combo）

#### 2.1.1 功能描述

从用户的知识体系中选取两个"距离较远"的概念，让 LLM 生成跨界联想和实践建议。

#### 2.1.2 详细流程

1. **构建概念池**：
   - 从 vault 所有笔记提取标签（`#tag` 和 `frontmatter.tags`），计算 TF-IDF 权重
   - 从笔记标题和高频词中提取关键词
   - 从已注册代码仓库中提取仓库名 + 主要技术栈（如 Rust、TypeScript、Python）

2. **选取两个概念**：
   - 第一个概念：随机选取（从概念池中按权重采样）
   - 第二个概念：与第一个概念标签共现度最低的 top-10 中随机选取（确保"距离远"但非完全无关）
   - 距离阈值可配置

3. **LLM 创意生成**：
   - 将两个概念及其来源信息组装成 prompt
   - LLM 生成跨界联想、具体实践建议、可能的实验方案

4. **结果附带链接**：
   - 附带与两个概念相关的笔记 Obsidian URI 链接
   - 附带相关代码仓库的 VSCode 跳转链接

#### 2.1.3 输入输出

**输入**：
```json
{
  "tool": "get_inspiration",
  "arguments": {
    "type": "concept_combo"
  }
}
```

**输出**：
```json
{
  "tool": "get_inspiration",
  "status": "success",
  "result": {
    "type": "concept_combo",
    "concept_a": {
      "term": "缓存替换策略",
      "source": "note",
      "source_path": "cs/cache-algorithms.md",
      "obsidian_uri": "obsidian://open?vault=brain&file=cs/cache-algorithms.md"
    },
    "concept_b": {
      "term": "睡眠实验",
      "source": "note",
      "source_path": "life/sleep-experiment.md",
      "obsidian_uri": "obsidian://open?vault=brain&file=life/sleep-experiment.md"
    },
    "inspiration": "试着用 LRU 缓存的思路优化你的睡眠实验数据记录：将最近 7 天的数据视为'热数据'保持高频记录，超过 7 天的自动降级为每周摘要——正如缓存淘汰冷数据。具体实践：1) 为每天的数据打'访问时间戳'；2) 超过 7 天未回顾的数据自动合并为周摘要；3) 观察哪些'冷数据'偶尔被'重新加载'（你偶尔想起的旧实验结论），这些可能是被低估的洞察。",
    "related_notes": [
      "cs/cache-algorithms.md",
      "life/sleep-experiment.md",
      "cs/data-structures.md"
    ],
    "related_repos": [
      {
        "name": "cache-sim",
        "vscode_uri": "vscode://file/Users/me/projects/cache-sim"
      }
    ],
    "generated_at": "2026-05-29T10:30:00Z"
  }
}
```

### 2.2 反向提问引擎（reverse_question）

#### 2.2.1 功能描述

选取一篇笔记（用户指定或系统自动选择最近修改的笔记），让 LLM 生成 3 个用户可能没想过的深入问题。

#### 2.2.2 详细流程

1. **选择目标笔记**：
   - 如果用户指定 `note_path`，使用该笔记
   - 如果未指定，选取最近修改的笔记（排除今日新创建的草稿，选择有实质内容的笔记）
   - 笔记字数需 > 200 字（过短的笔记不适合提问）

2. **内容分析**：
   - 提取笔记的核心论点和关键概念
   - 识别笔记中引用的其他笔记（`[[wikilinks]]`）
   - 获取笔记的标签和所属领域

3. **LLM 生成问题**：
   - 问题应与笔记内容相关但超越表面
   - 问题类型包括：假设反事实、延伸应用场景、逻辑一致性检验、时间维度推演
   - 每个问题附带简短的"为什么这个问题值得思考"说明

4. **结果附带上下文**：
   - 附带原笔记链接
   - 附带与问题相关的其他笔记链接（如有）

#### 2.2.3 输入输出

**输入**：
```json
{
  "tool": "get_inspiration",
  "arguments": {
    "type": "reverse_question",
    "note_path": "essays/sleep-experiment.md"
  }
}
```

**输出**：
```json
{
  "tool": "get_inspiration",
  "status": "success",
  "result": {
    "type": "reverse_question",
    "note": {
      "path": "essays/sleep-experiment.md",
      "title": "我的睡眠实验：30天早睡记录",
      "obsidian_uri": "obsidian://open?vault=brain&file=essays/sleep-experiment.md"
    },
    "questions": [
      {
        "question": "如果你的睡眠数据中，'感觉良好'和实际睡眠时长呈负相关——即睡得少反而感觉好——你会如何解释这个反直觉的现象？",
        "why_it_matters": "你的笔记假设了'睡够 8 小时最好'，但数据可能揭示压力激素（皮质醇）的短期提升效应，这会挑战你的核心假设。",
```

### 2.3 对立观点生成器（counterpoint）

#### 2.3.1 功能描述

对指定笔记生成反方观点，识别逻辑漏洞和未覆盖的论证角度，帮助用户完善论证或发现盲点。

#### 2.3.2 详细流程

1. **选择目标笔记**：
   - 必须指定 `note_path`（对立观点需要明确的靶子）
   - 笔记需包含论点或观点（纯数据记录型笔记不适合此模式）
   - 笔记字数需 > 300 字

2. **论证结构分析**：
   - LLM 识别笔记中的核心主张、支撑论据、隐含假设
   - 标记论证中的薄弱环节（样本量小、缺乏反例讨论、过度概括等）

3. **LLM 生成对立观点**：
   - 对每个核心主张生成至少一个反方观点
   - 指出逻辑漏洞和未考虑的替代解释
   - 提供完善论证的具体建议

4. **结果结构化**：
   - 按"主张 → 反方 → 建议"组织
   - 附带原笔记链接和相关参考

#### 2.3.3 输入输出

**输入**：
```json
{
  "tool": "get_inspiration",
  "arguments": {
    "type": "counterpoint",
    "note_path": "essays/ai-future.md"
  }
}
```

**输出**：
```json
{
  "tool": "get_inspiration",
  "status": "success",
  "result": {

    "note": {
      "path": "essays/ai-future.md",
```

### 2.4 统一工具接口

#### 2.4.1 接口定义

所有灵感模式通过统一的 `get_inspiration` 工具暴露：

```
get_inspiration(type?, note_path?)
```

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `type` | `string` | 否 | `"concept_combo"` | 灵感模式：`"concept_combo"` / `"reverse_question"` / `"counterpoint"` |
| `note_path` | `string` | 否 | 自动选择 | 目标笔记路径（vault 内相对路径） |

#### 2.4.2 参数校验规则

| 模式 | `note_path` 要求 | 笔记字数要求 | 说明 |
|---|---|---|---|
| `concept_combo` | 不需要（忽略） | N/A | 系统自动构建概念池 |
| `reverse_question` | 可选（默认最近修改） | > 200 字 | 过短的笔记不适合提问 |
| `counterpoint` | 必填 | > 300 字 | 需要足够内容才能生成有意义的对立观点 |

#### 2.4.3 错误响应

```json
{
  "tool": "get_inspiration",
  "status": "error",
  "error": {
    "code": "NOTE_TOO_SHORT",
    "message": "笔记 'essays/draft.md' 内容过短（120字），反向提问需要至少 200 字",
    "suggestion": "请选择内容更丰富的笔记，或先补充笔记内容"
  }
}
```

### 2.5 灵感历史记录

#### 2.5.1 功能描述

每次灵感生成的输入和输出都保存到 SQLite 的 `inspiration_history` 表中，用于：
- 避免重复生成相同的概念组合
- 用户回顾过去的灵感
- 追踪创意多样性和模式分布

#### 2.5.2 记录内容

| 字段 | 说明 |
|---|---|
| `id` | UUID 唯一标识 |
| `type` | 灵感模式 |
| `input_refs` | JSON 格式，包含输入引用（概念/笔记路径） |
| `output` | LLM 生成的完整输出文本 |
| `created_at` | 生成时间戳 |

## 3. 用户故事

### US-01：晨间灵感触发

**角色**：个人知识工作者
**场景**：每天早晨开始工作前，用户打开 Claude Desktop 并通过 MCP 连接 ObsidianBrain
**操作**：用户说"给我来点灵感"，LLM 自动调用 `get_inspiration(type: "concept_combo")`
**期望**：
- 系统从用户的知识库中选取两个意想不到的概念组合
- 生成一段跨界联想和具体的实践建议
- 附带 Obsidian 链接，用户可以快速跳转到相关笔记深入思考
**价值**：以一次"知识碰撞"开启一天的工作，打破信息茧房

### US-02：写作深化

**角色**：技术博客作者
**场景**：用户正在写一篇关于 Rust 异步编程的文章（`programming/rust-async.md`），感觉内容不够深入
**操作**：用户说"帮我审视一下这篇笔记有什么没想清楚的地方"，LLM 调用 `get_inspiration(type: "reverse_question", note_path: "programming/rust-async.md")`
**期望**：
- 系统生成 3 个用户可能没想过的问题
- 问题超越表面，可能涉及异步编程的哲学基础、与其他语言的对比、未来演进方向
- 用户被启发后补充笔记内容，提升文章深度
**价值**：帮助作者发现自己思维中的盲区，丰富文章内容

### US-03：论证完善

**角色**：独立思考者
**场景**：用户在笔记中写了一篇关于"远程办公将成为主流"的论述文章（`essays/remote-work-future.md`）
**操作**：用户说"帮我找找这篇文章的漏洞"，LLM 调用 `get_inspiration(type: "counterpoint", note_path: "essays/remote-work-future.md")`
**期望**：
- 系统生成系统的反方观点
- 指出逻辑漏洞：样本偏差（硅谷视角 vs 全球视角）、未考虑的因素（孤独感、协作创新损失）
- 提供完善论证的具体建议
**价值**：像有一个"魔鬼代言人"帮你完善思考

### US-04：跨项目灵感

**角色**：全栈开发者
**场景**：用户同时维护多个代码仓库（一个 Rust 系统工具、一个 TypeScript Web 应用、一个 Python 数据分析项目）
**操作**：用户说"给我一些跨界灵感"，LLM 调用 `get_inspiration(type: "concept_combo")`
**期望**：
- 概念池包含代码仓库的技术栈信息
- 可能选出"Rust 的所有权模型"和"React 状态管理"的组合
- LLM 生成类比：将 Rust 的借用检查器思想应用到前端状态管理中（不可变状态 + 明确的变更路径）
**价值**：技术栈之间的交叉启发

### US-05：研究笔记审视

**角色**：学术研究者
**场景**：用户在阅读一篇重要论文后写了详细笔记（`research/attention-is-all-you-need.md`），想要深入思考
**操作**：用户说"对这篇论文笔记提几个深刻的问题"，LLM 调用 `get_inspiration(type: "reverse_question", note_path: "research/attention-is-all-you-need.md")`
**期望**：
- 生成的问题触及论文的根本假设（如"为什么 self-attention 是 O(n²)？有没有理论下界？"）
- 引导用户思考论文未解决的问题
- 可能与用户其他笔记产生关联（如与 `cs/complexity-theory.md` 交叉）
**价值**：深化对学术文献的理解，发现潜在研究方向

### US-06：灵感回顾

**角色**：知识管理者
**场景**：用户在每周回顾时想看看这周产生了哪些灵感
**操作**：LLM 查询灵感历史记录，总结本周的灵感产出
**期望**：
- 能看到本周所有灵感记录
- 标注哪些灵感已经被用户付诸实践（后续可扩展标记功能）
- 分析灵感类型分布和概念多样性
**价值**：追踪创意的积累和演变

### US-07：日记式灵感触发

**角色**：反思型学习者
**场景**：用户在日记中记录了一天的思考（`journal/2026-05-28.md`），想从日记中发掘更深的意义
**操作**：用户说"从我今天的日记中找点灵感"，LLM 调用 `get_inspiration(type: "reverse_question", note_path: "journal/2026-05-28.md")`
**期望**：
- 系统从日记中提取隐含的情感模式和思考主题
- 生成的问题帮助用户反思（如"你今天两次提到'时间不够用'——这是客观限制还是优先级问题？"）
- 与用户的时间管理笔记产生关联
**价值**：将日常反思提升为深层自我认知

### US-08：头脑风暴前的热身

**角色**：产品经理/创意工作者
**场景**：用户即将开始一个新项目的头脑风暴，想要先"热身"思维
**操作**：用户说"给我几个意想不到的概念组合来热身"，LLM 连续调用 2-3 次 `get_inspiration(type: "concept_combo")`
**期望**：
- 每次返回不同的概念组合
- 灵感历史管理器确保不重复
- 用户进入"发散思维"状态后开始正式头脑风暴
**价值**：像运动员热身一样，用跨界碰撞激活创意思维

---

## 4. 非功能需求

### 4.1 响应时间

| 操作 | 目标延迟 | 说明 |
|---|---|---|
| 概念池构建（首次） | < 2s | 需扫描所有笔记提取标签，可使用缓存 |
| 概念池构建（缓存命中） | < 50ms | 从内存缓存读取 |
| 概念选取 + 距离计算 | < 100ms | 基于预计算的距离矩阵 |
| LLM 创意生成 | 取决于 API | 超时上限 30s，支持流式输出 |
| 结果格式化 + 链接生成 | < 50ms | 纯本地计算 |
| **端到端（不含 LLM）** | **< 300ms** | 符合顶层设计 P95 < 500ms 的要求 |

### 4.2 创意多样性

- **概念覆盖**：连续 10 次 `concept_combo` 调用应覆盖至少 8 个不同的概念（不重复使用同一概念作为 concept_a）
- **模式平衡**：历史记录中三种模式的比例不应严重失衡（用户自由选择的前提下）
- **去重机制**：相同的概念对（A, B）在 7 天内不应重复出现（顺序无关，即 (A, B) 和 (B, A) 视为相同）
- **问题多样性**：`reverse_question` 生成的 3 个问题应分属不同类型（假设反事实、延伸应用、逻辑检验等）

### 4.3 可用性

- 当 LLM API 不可用时，返回友好的错误信息和建议（"LLM 暂时不可用，请稍后重试"）
- 当概念池为空（vault 中无标签/关键词）时，提示用户先积累笔记内容
- 笔记路径无效时，返回错误并建议有效的笔记列表

### 4.4 资源占用

- 概念池缓存内存 < 10MB（假设 10,000 个标签/关键词）
- 距离矩阵内存 < 50MB（假设 1,000 个核心概念，稀疏存储）
- 灵感历史记录 SQLite 存储 < 100MB（假设每天 10 条，保留 1 年）

## 5. 与其他模块的接口

### 5.1 记忆引擎（Memory Service）

灵感熔炉从记忆引擎获取以下数据：

| 数据 | 用途 | 接口 |
|---|---|---|
| 全量标签列表 | 构建概念池的标签维度 | `memory.get_all_tags() -> Vec<(String, u32)>` |
| 笔记关键词 | 构建概念池的关键词维度 | `memory.get_note_keywords(path) -> Vec<String>` |
| 记忆搜索结果 | 获取与概念相关的笔记 | `memory.search(query, top_k) -> Vec<Memory>` |
| 笔记内容 | 提供给 LLM 作为上下文 | `memory.get_note_content(path) -> String` |

### 5.2 时间线（Timeline Service）

灵感熔炉从时间线获取以下数据：

| 数据 | 用途 | 接口 |
|---|---|---|
| 近期修改的笔记 | `reverse_question` 自动选择目标笔记 | `timeline.get_recent_notes(days: 7) -> Vec<NoteInfo>` |
| 历史同期笔记 | 作为 `concept_combo` 的额外素材 | `timeline.get_notes_around_date(date) -> Vec<NoteInfo>` |

### 5.3 代码仓管理（CodeRepo Service）

灵感熔炉从代码仓获取以下数据：

| 数据 | 用途 | 接口 |
|---|---|---|
| 仓库列表 | 构建概念池的技术概念维度 | `code_repo.list_repos() -> Vec<CodeRepo>` |
| 仓库技术栈 | 丰富技术概念描述 | `code_repo.get_language_stats(name) -> HashMap<String, f32>` |
| 仓库关联笔记 | 结果中附带相关链接 | `code_repo.get_linked_notes(name) -> Vec<PathBuf>` |

### 5.4 LLM 客户端（LLM Client）

灵感熔炉调用 LLM 客户端生成创意内容：

| 操作 | 接口 |
|---|---|
| 概念组合创意 | `llm.generate(prompt, temperature: 0.9) -> String` |
| 反向提问 | `llm.generate(prompt, temperature: 0.8) -> String` |
| 对立观点 | `llm.generate(prompt, temperature: 0.7) -> String` |

不同模式使用不同的 temperature：概念组合需要更高的创造性（0.9），对立观点需要更高的严谨性（0.7）。

### 5.5 SQLite 存储

灵感历史记录存储在 `inspiration_history` 表中（见 [top_design.md §4.6](../top_design.md)）。

## 6. 约束与假设

### 6.1 假设

| 编号 | 假设 | 验证方式 |
|---|---|---|
| A-01 | 用户的 vault 中有足够多的笔记（> 20 篇）来构建有意义的概念池 | 启动时检查，提示用户积累 |
| A-02 | 笔记使用标签系统（`#tag` 或 `frontmatter.tags`）来组织内容 | 支持无标签的降级方案（纯关键词） |
| A-03 | LLM 能基于结构化 prompt 生成高质量的跨界联想 | 多模板 + 用户反馈迭代 |
| A-04 | 标签共现度可以近似表示概念间的"距离" | 后续可引入语义向量距离作为补充 |
| A-05 | 用户有稳定的网络连接以调用 LLM API | 支持本地 LLM（Ollama）作为备选 |
| A-06 | 概念池不需要实时更新——每次灵感调用时使用最近一次缓存即可 | 缓存 TTL 1 小时，可配置 |

### 6.2 约束

| 编号 | 约束 | 原因 |
|---|---|---|
| C-01 | 概念池大小上限 5,000 个概念 | 控制距离矩阵计算复杂度 |
| C-02 | LLM prompt 长度上限 4,000 token | 控制 API 调用成本 |
| C-03 | 灵感历史保留期限 1 年 | 控制 SQLite 存储大小 |
| C-04 | `counterpoint` 模式必须指定笔记路径 | 对立观点需要明确的靶子 |
| C-05 | 单次调用 LLM 超时上限 30s | 防止长时间阻塞 |

## 7. 验收标准

### 7.1 功能验收

| 编号 | 验收项 | 通过条件 |
|---|---|---|
| AC-01 | `concept_combo` 能正常返回结果 | vault 有 > 20 篇带标签笔记时，调用返回两个不同概念 + 创意联想 |
| AC-02 | `concept_combo` 概念距离合理 | 选取的两个概念标签共现度 < 0.1（低共现度） |
| AC-03 | `reverse_question` 生成 3 个问题 | 返回的 3 个问题不重复，且与笔记内容相关 |
| AC-04 | `counterpoint` 生成对立观点 | 返回至少 2 个反方观点，且包含逻辑分析 |
| AC-05 | 自动笔记选择 | 不指定 `note_path` 时，自动选择最近修改的有实质内容的笔记 |
| AC-06 | Obsidian 链接正确 | 所有链接能正确打开对应笔记 |
| AC-07 | 历史记录写入 | 每次调用成功后，`inspiration_history` 表有对应记录 |
| AC-08 | 去重机制 | 7 天内相同的概念对不重复出现 |
| AC-09 | 参数校验 | `counterpoint` 不指定笔记时返回明确错误信息 |
| AC-10 | 错误降级 | LLM API 不可用时返回结构化错误信息 |

### 7.2 性能验收

| 编号 | 验收项 | 通过条件 |
|---|---|---|
| PA-01 | 概念池缓存命中时端到端延迟（不含 LLM） | < 300ms (P95) |
| PA-02 | 概念池首次构建 | < 2s（1,000 篇笔记规模） |
| PA-03 | 内存占用 | 概念池 + 距离矩阵 < 60MB |

### 7.3 质量验收

| 编号 | 验收项 | 通过条件 |
|---|---|---|
| QA-01 | 创意多样性 | 连续 10 次调用覆盖至少 8 个不同概念 |
| QA-02 | 问题质量 | 人工评估 10 组 `reverse_question` 输出，> 70% 的问题被评为"有启发性" |
| QA-03 | 对立观点深度 | 人工评估 10 组 `counterpoint` 输出，> 70% 的反方观点被评为"有价值" |

## 8. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
|---|---|---|---|
| 概念池质量差（标签噪音多） | 灵感输出低质量 | 中 | TF-IDF 过滤低频标签；人工可配置黑名单 |
| LLM 生成的跨界联想过于牵强 | 用户体验差 | 中 | 调整 prompt 要求"合理且有启发性"；temperature 可调 |
| 笔记太少导致概念池不够丰富 | 无法生成有意义的组合 | 高（新用户） | 概念池不足 20 个概念时给出友好提示，引导用户先积累笔记 |
| 距离矩阵计算复杂度过高 | 首次启动慢 | 低 | 概念池大小上限 5,000；稀疏矩阵存储 |
| LLM API 费用 | 频繁调用灵感功能增加成本 | 低 | 单次 prompt < 4,000 token；使用 gpt-4o-mini 控制成本 |

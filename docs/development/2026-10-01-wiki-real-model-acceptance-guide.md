## 1. 目标与完成边界

本阶段不再扩建一套 Agent，也不继续无限补充边缘功能。目标是回答三个可验证的问题：

1. 当前供应商下，问答与研究是否能稳定取得足够证据、产出完整且有用的内容？
2. 长任务中断、输出截断或来源更新时，是否保留已有成果，只恢复需要处理的阶段？
3. 报告和下载的 PPT 是否真正可用，而不仅是结构校验通过？

实施顺序：**隔离环境与案例准备 → 第一批真实验收 → 第二批按证据修复 → 回归与交付**。章节并发、更大页数范围等增强项单独排期，不作为本轮完成的前提。

本轮范围包括 Markdown 书籍的来源管理、语义 Wiki、问答、研究报告与 PPT 下载。保持 DeepSeek Harness 为 Agent 执行器。不引入 PDF 摄入、Claude Code 运行时、前端 PPT 预览或另一套自主决策循环。

上游设计依据：[顶层设计](../top_design.md)、[REQ-08](../requirement/08-llm-wiki.md)、[DEV-08](08-llm-wiki.md)。此前预算改造见 [研究预算计划](2026-09-28-flexible-research-budget-plan.md) 和 [问答空输出计划](2026-09-28-qa-empty-output-budget-plan.md)。

## 3. 准备阶段：隔离数据和冻结基线

### 3.1 安全原则

- 使用新建临时数据目录、独立数据库、独立来源目录和空闲端口，不连接正式书架。
- 测试来源使用专门准备的材料，或经许可复制的脱敏材料。不要向正在使用的书架注入用例，不修改原书。
- 不直接复制正在写入的 SQLite 文件；确需使用正式数据快照时，先通过现有备份功能取得一致快照，在隔离实例恢复并重新检查保存的路径。
- 不覆盖个人配置、Skill、API Key 或供应商额度。不把密码、完整 Prompt、私密原文写入提交中的验收报告。
- 外部检索默认关闭。需要验证外部取证时，只授权测试任务所需域名和有限请求次数。
- 真模型验收会调用配置的供应商，执行前明确模型、案例、调用范围及费用控制方式；确定性故障测试不消耗模型额度。

### 3.2 隔离启动方法

以下为 macOS/zsh 示例。先检查 `19988` 端口未占用；若占用，替换为空闲端口。不要停止其他实例腾端口。

前端构建与后端嵌入目录必须一致：当前后端使用的是 `frontend/dist_new`，不是默认 `dist`。

```bash
cd /Users/tiercelchow/Documents/WorkSpace/MyProjects/ObsidianBrain/frontend
npm run build -- --outDir dist_new
```

另一个终端中，创建隔离目录并前台启动：

```bash
cd /Users/tiercelchow/Documents/WorkSpace/MyProjects/ObsidianBrain/backend
WIKI_ACCEPTANCE_DIR=$(mktemp -d "${TMPDIR:-/tmp}/obsidianbrain-wiki-acceptance.XXXXXX")
mkdir -p "$WIKI_ACCEPTANCE_DIR/vault"
echo "$WIKI_ACCEPTANCE_DIR"
OBRAIN_DATA_DIR="$WIKI_ACCEPTANCE_DIR/data" \
OBRAIN__STORAGE__DB_PATH="$WIKI_ACCEPTANCE_DIR/data/brain.db" \
OBRAIN__VAULT__PATH="$WIKI_ACCEPTANCE_DIR/vault" \
OBRAIN__VAULT__WATCH_ENABLED=false \
OBRAIN__OBSIDIAN__ENABLED=false \
cargo run -- --host 127.0.0.1 --port 19988
```

访问 `http://127.0.0.1:19988`，由该实例提供前端与 API，避免代理串到正式数据库。启动日志必须确认 SQLite 路径属于刚创建的目录；确认前先不添加书架或创建任务。

重要约束：

- 层级环境变量是 `OBRAIN__STORAGE__DB_PATH`，前缀后有两个下划线。少一个不会正确隔离数据库。
- `OBRAIN_DATA_DIR` 还隔离成果文件、缩略图和应用日志；仅指定数据库路径不足以隔离全部产物。
- 不使用 `config set` 来代替本步骤的启动配置。该命令走数据目录下的默认数据库路径，和启动时单独指定的数据库路径不是同一个选择入口。
- 当前 Vite 开发代理固定指向 `9876`。不能直接打开原有 `5173` 页面并假定它指向隔离实例。若必须热更新，需单独配置测试代理，并明确核对实际后端地址。
- 若恢复了旧数据库，其保存的系统配置可能包含原 Vault/Obsidian 地址；必须在隔离实例重新核对，不得因为环境变量已设置就假定所有保存配置都安全。
- 验收结束后保留目录及结果，停止本次前台进程即可；本指导不要求删除任何目录。

在隔离实例重新配置已有供应商及 Harness，检查可执行文件路径和连接。复用已有密钥环境变量时不要打印值。检查 Agent 临时工作区和工具能力令牌只关联本次测试书籍，不给 Agent 额外的个人文件访问权限。

### 3.3 模型能力记录

冻结一组供应商/模型配置作为首轮基线，并记录：

- provider/model 标识、Harness 版本、运行配置版本；不记录密钥。
- 声明的上下文容量、单次最大输出、推理策略，以及 ACP 实际报告的能力。
- 当前 Prompt、Skill 的版本或内容哈希及实际绑定状态。
- 代码提交、来源版本、知识库 revision、编译与审核状态。

不要把“支持 1M 上下文”等同于“可以输出 1M tokens”。当前未知上下文的应用默认值是 `1,048,576`，应用单次输出护栏为 `262,144`；两者不是供应商能力承诺。预算必须受到实际模型能力与供应商限制约束。

首轮保持配置不变；修改模型或预算后另建记录，不把两个配置的结果混成一次验收。

### 3.4 测试材料

准备一组约 8–12 篇 Markdown：同一主题跨章节出现、术语别名、前提条件、版本差异、反例、比较表、公式、可追溯数值，以及明确不存在的知识点。规模是验收材料建议，不是产品召回上限。

编写一份人工核对表，列出每个问题的关键事实、原文位置、必要条件和禁止得出的结论。先确定核对表，再看模型结果，避免把模型答了什么当作它应该答什么。

先同步来源、智能编译并人工审核，确保测试 Wiki 已发布；保留编译前后的来源/条目对应关系。这样能分辨“编译漏掉”和“问答没检索到”，而不是一律调整召回数量。

## 4. 第一批：真实供应商效果验收

### 4.1 执行原则

首轮每例运行一次，失败后先定位，不立即重复点击。疑似偶发问题再补跑两次，保留全部结果。大研究与 PPT 优先安排在前面几个基础用例通过后，控制无效消耗。

以下问题用 VLLM/推理书籍举例；若测试书内容不同，替换主题，但保留用例所考察的结构。没有答案的材料不能被用来要求模型编造答案。

| 编号 | 范围与操作 | 重点验收 |
| --- | --- | --- |
| W1 | 同步并编译含跨章同义概念、条件冲突和数值的材料 | 形成语义主题而非只复制目录；关键主张有来源，冲突不被强行统一；审核前不成为正式知识 |
| Q1 | “解释 KV Cache 的主要作用及局限，用书中材料回答。” | 先利用已编译知识，按需要取原文；关键事实和条件齐全，引用可打开且支持对应结论 |
| Q2 | “比较两种缓存/调度策略，说明适用条件、代价和反例。” | 跨章节召回，不只停在首条匹配；没有资料的比较维度明确标缺失 |
| Q3 | 连续追问：“先给概览”→“只讨论低延迟在线服务”→“那它和前一种方法相比呢？” | 记住限定范围和指代；不把上一轮完整候选目录或工具结果重复塞入长期历史 |
| Q4 | 提问一个资料明确未覆盖的版本/产品性能 | 说明证据不足，不虚构实测数据；仅在授权范围补充取证，不把常识冒充书内证据 |
| R1 | 深度研究：包含机制、比较、条件、反例等 4–6 个子题 | 创建前可确认目标；子题上下文独立；章节有实质内容；综合检查覆盖所有主题，不抹平冲突 |
| R2 | 决策报告：“面向团队负责人，给出方案选择、风险与验证步骤。” | 先结论后依据；区分事实/推断/建议；建议有成立条件和下一步，不是泛泛总结 |
| P1 | 用 R2 的结果交付决策型 PPT，确认受众、重点与主题 | 页面形成决策叙事，关键条件未丢失；可下载、打开且无文字遮挡；不是每页同一段摘要 |
| P2 | 教学型 PPT：“面向初学者，用机制图和一个例子解释主题。” | 层次由浅入深；图示说明关系而非装饰；有依据的数据才生成数值图表 |
| W2 | 在隔离来源中修改一条已引用事实，同步并执行 refresh/review | 保留旧版引用，提示当前变化；失效/恢复范围准确，不影响无依赖章节或其他书籍 |
| R3 | 研究至少保存一章后取消，再显式恢复；另测测试服务重启恢复 | 已完成章不重跑、不改成果身份；只恢复待处理阶段；迟到输出不能覆盖新执行 |

P1/P2 不必重复整份研究，可以复用已保存报告，但记录是哪一版报告及何时生成演示成果。若界面不支持直接复用此交付路径，通过对应测试夹具复用，不为验收擅自新增产品入口。

### 4.2 故障验收单独执行

采用 Fake Runtime/ACP 夹具模拟，不通过反复降低真实预算制造收费失败：

1. `max_tokens` 且有正文：保留未发布内容，阶段内扩容有上限，只重做当前阶段。
2. `max_tokens` 且无正文：准确说明没有可展示正文，不把检索列表当作答案。
3. 单次输出硬限：调用前或确认能力后明确停止，不反复以相同预算请求。
4. `max_turn_requests`：说明轮次受限，不把它归因于输出 token 不足。
5. 格式错误：只进行有限合同修复，不能拼接多个残缺 JSON 或吞掉未知字段。
6. 取消、启动/空闲/总超时、权限拒绝：终止类别准确，不能统一当作 token 截断扩容。
7. 完成正文但入库失败：有恢复入口，恢复正文不再调用模型；避免重复消息。
8. 历史阶段、错误任务/Run、页面关闭后的迟到响应：无跨任务内容泄漏，无弹窗重开或抢焦点。

已有测试能覆盖的部分先运行回归；仅为新发现补测试，不重新实现另一套故障框架。

### 4.3 内容验收标准

每例按以下五个维度标注“通过 / 需修改 / 失败”，附原文依据，不用一个综合分掩盖严重问题：

1. **覆盖**：人工核对表中的关键事实、比较维度、前提与反例是否覆盖。
2. **可追溯**：关键结论能否回到实际读取的来源与版本；抽查引用是否真的支持结论，而不仅是编号有效。
3. **准确与边界**：是否区分事实/推断/建议，是否保留限制和未知信息。
4. **任务适配**：是否符合受众、用途、深度、重点，以及多轮用户新增约束。
5. **完整与可用**：是否形成完整答案或报告，而不是检索罗列、套话和重复段落。

记录人工期望来源集合和实际读取集合。遗漏时检查来源是否进入编译条目、是否出现在候选、是否被工具读到、是否被输出使用，逐层定位。小样本只能说明这些案例的表现，不应宣称全局召回率。

### 4.4 PPT 实际显示验收

结构校验与视觉验收分别记录。下载最终 `.pptx`，用现有 PowerPoint、Keynote 或可用的离线渲染工具打开/逐页检查；没有工具时报告“未完成视觉验收”，不能以 ZIP 合法代替。

检查清单：

- 标题、正文、引用、小字、长术语和公式是否遮挡、截断或超出页面。
- 所用字体是否可用；发生字体替换后是否仍能正常排版。
- 至少有适合内容的几类版式，但不为追求版式数强行插图。
- 每页有清楚的结论/作用，页与页之间有推进，避免重复标题与重复 takeaway。
- 图表数值、单位、比较条件能追溯，缺数据时改用机制/关系图，不虚构数据。
- 策划 JSON 中的重要信息确实可见；生成器不得无提示丢弃正文项。
- 关键信息投影后的遗漏在运行记录可解释；不能宣称完整使用了未读到的材料。
- 下载文件和报告版本相符，重复下载可打开。

保存脱敏的报告、PPT、逐页截图及问题页码。当前页数合同为 4–12 个内容页、每页最多 700 字符；这是现有生成器约束，不是理想设计标准。若内容确实被此约束损害，另列问题并分析是否需要调整，不能只让 Prompt 生成更长内容却不改校验/渲染。

## 5. 第二批：依据失败证据修改

### 5.1 先区分问题类型

| 观察到的问题 | 首先检查 | 允许的定向修改 |
| --- | --- | --- |
| 编译没覆盖关键概念 | 来源抽取、编译选材、变更集及审核内容 | 修编译合同/选材或语义规则，不先扩大问答预算 |
| Wiki 有内容但没被检索 | 候选目录、别名、范围、工具实际读取 | 优化候选说明与工具取证策略，允许按缺口扩展 |
| 读到了但结论错误/空泛 | 实际 Prompt、Skill、证据条件与受众要求 | 改答案组织和核对规则，不以更多 token 掩盖错误 |
| 正文空且 `max_tokens` | 请求参数、推理消耗、能力声明、ACP 终止 | 校准正文/推理余量与恢复提示，不一律关闭推理 |
| 轮次耗尽 | 重复工具调用、目录分页、当前轮次策略 | 减少重复输入/调用，必要时调整轮次；不套输出扩容 |
| 首字慢 | 排队、进程启动、规划、检索、供应商响应 | 分段观测后修最慢环节，不能只延长总超时 |
| PPT 字少、重复、白底罗列 | 报告质量、选材投影、策划合同、主题及渲染 | 调整叙事/信息密度/版式载荷，不能靠增加装饰填空 |
| 更新后整份重跑或结果串版 | 来源依赖、revision、阶段租约与成果身份 | 修选择性失效和恢复，不放松版本/作用域校验 |

优先级：数据串书、错误引用、完成成果丢失、权限越界属于 P0；核心任务无法完成或内容严重失真属于 P1；排版、措辞、效率改进属于 P2。本轮必须关闭 P0/P1，P2 记录后定向处理。

### 5.2 工作包 A：校准容量与运行策略

**触发条件**：真实运行有证据表明实际申请空间不足、能力选错、时间配置与输出不匹配，或恢复重复消耗。

主要位置：

- `backend/src/models/agent_budget.rs`：共享上下文/输出护栏与时间规划。
- `backend/src/core/book_wiki/qa_policy.rs`：问答资源、意图和输出目标。
- `backend/src/core/book_wiki/research_policy.rs`：章节、综合、结构与推理余量。
- `backend/src/core/book_wiki/research_workflow.rs`：阶段扩容、合同修复与恢复边界。
- `backend/src/infra/deepseek_harness.rs`：请求能力、ACP 流与终止原因。

实施要求：

1. 把“期望正文长度”“实际请求上限”“供应商能力”“实际 usage”分开，不增加一个全局超大常量解决所有任务。
2. 实测更小容量必须生效；能力未知时明确采用应用规划值，不假定供应商支持。
3. 问答按问题复杂度、证据缺口和用户预期调整，不固定每题召回数。Harness 保留取证与继续/停止决策。
4. 扩容只针对明确输出截断，并受完整输入和真实硬限约束。取消、拒绝、权限、轮次和数据库错误不得借扩容重试。
5. 更换模型/供应商后重新规划，不继承不适用的旧容量；保留已完成正文和阶段检查点。
6. 超时修改必须有阶段耗时证据，不能让卡住任务无限挂起。

先增加边界测试再修代码：小模型硬限、未知能力、长中文/公式输入、连续截断有界停止、恢复换模型、输出完成但保存失败，以及取消和租约失效。随后回跑受影响的真模型案例。

### 5.3 工作包 B：报告和 PPT 的编辑质量

**触发条件**：结构合法但内容重复、逻辑弱、条件丢失，或真实文件排版不可用。

主要位置：

- `backend/prompts/wiki/answer.md`、`research.md`、`presentation.md`。
- `backend/skills/book-query/SKILL.md`、`book-research/SKILL.md`、`book-presentation/SKILL.md`。
- `backend/src/core/book_wiki/presentation_material.rs`：完整报告与受保护投影。
- `backend/src/core/presentation.rs`：策划合同、版式载荷与 PPTX 渲染。
- `backend/src/infra/sqlite_store.rs` 及新迁移：已安装 Prompt/Skill 的更新路径。

报告规则：回答目标优先；每章增加独立价值；事实与建议分开；比较维度一致但保留适用条件；综合消除重复，不删除争议和来源；不把模型自报的核对结果冒充独立事实验证。

PPT 规则：从报告提取叙事主线；受众/目的影响章节和版式；标题表达本页结论；图表必须有数据，关系图必须有机制；同一证据可以复用，但不能用同一段摘要填满整份演示。控制文字量与引用区尺寸；条件、单位、公式及版本不能在投影或排版中静默丢失。

修改 Prompt/Skill 时必须覆盖运行时真实绑定的内容：只改仓库文件而不更新已有数据库的发布内容，会造成页面与执行不一致。采用新的、可测试的迁移/种子更新；不改写已经执行过的历史迁移，不手工改正式数据库。验证全新数据库、旧版升级、重复启动，以及后续用户发布版本的保护策略。

增加合同与渲染边界测试后，重新生成至少一份决策 PPT 和一份教学 PPT，逐页视觉复查；不能只根据 JSON 测试宣布内容改善。

### 5.4 工作包 C：只补真实暴露的界面缺口

主要位置：

- `frontend/src/views/knowledge/KnowledgeChat.vue`：状态、流式正文、历史与恢复。
- `frontend/src/views/knowledge/KnowledgeTasks.vue`：任务简报确认与交付类型。
- `frontend/src/components/knowledge/KnowledgeResearchWorkspace.vue`：阶段、历史成果、失败原文。
- `frontend/src/components/knowledge/KnowledgeRunInspector.vue`：能力/预算/证据/终止原因。
- `frontend/src/api/knowledge.ts`：窄接口与共享类型。

用户应能回答四个问题：现在在做什么；哪些成果已经保存；失败后还能看什么；点恢复会重做哪一部分。过程展示只表达可观察状态，不展示或伪造隐式思考链。

必须验证桌面及手机：内容可滚动、底部操作不截断、长错误不溢出；切换任务、历史版本或关闭弹窗后旧响应不得污染新视图。样式沿用系统组件，不另建一套控件。

### 5.5 条件性工作包：自动拆分超大子题

**不是本轮默认必做项。** 只有正确配置容量、扩容和合理规划后，真实材料仍持续让单个子题超过模型硬限，才进入这项开发。短期可先明确提示用户缩小范围，而不是偷偷丢内容。

若开发，先写需求和迁移设计，再实施：

1. 只拆分未完成的那个子题，保留其他已完成章；新规划拥有独立 revision，旧版可回看。
2. 子题有稳定父子身份和验收要求，不能把原标题拆成几段却丢失比较目标。
3. 自动拆分次数/叶子数有上限，拆后仍放不下则明确停止，不递归无限调用。
4. 综合 manifest 能说明原题覆盖了哪些叶子、缺哪些部分；不能把失败子题直接标完成。
5. 来源版本、引用范围、content_run_id、取消、epoch、租约与幂等保存规则继续成立。
6. 问答不因该功能被改造成强制章节流程；两种产品形态仍保持各自交互。

最低测试：中间子题超限但其他章不重做；拆后仍超限有界停止；取消发生在拆分中；服务重启恢复；原文更新只失效依赖叶子；旧计划和旧输出仍可查看；并发迟到结果不能覆盖新 revision。

## 6. 与“直接打开文件夹问 Agent”的对照

这是产品价值验证，不是新增 Claude Code 执行器。只有本机已有可用工具且获准使用时，才做同资料、同任务的对照；没有就标注未执行，不影响基础产品验收。

选择 Q2、R2、W2/R3 对应的任务。保持来源快照、请求、受众和输出要求一致；尽量使用相同模型，做不到则记录差异，不把差异全归功于架构。

比较的重点：

- 人工核对表的关键事实、条件和反例是否遗漏。
- 引用定位及版本能否验证，用户是否要手工找出处。
- 来源变化后，旧结论是否能追踪并选择性更新。
- 中断恢复需要重做多少已完成内容、多少人工操作。
- 完成同样目标的耗时、模型调用/可用 usage、人工修改次数。
- 成果能否在后续问答和研究复用，知识回写是否经过审核。

不以答案更长、工具调用更多或耗费 tokens 更多来定义优势。Wiki 应体现持久知识、可追溯来源和恢复能力，不承诺同一个模型因此必然更聪明。

## 7. 开发与回归流程

每个已确认缺陷单独处理：**定位证据 → 失败测试 → 最小修改 → 单元/集成回归 → 受影响真模型案例 → 文档与提交**。优先复用现有夹具，避免把收尾变成全局重构。

后端在 `backend/` 执行：

```bash
cargo fmt -- --check
cargo clippy -- -D warnings
cargo test --quiet
```

前端在 `frontend/` 执行：

```bash
npm test
npm run build
```

需要重测嵌入式界面时重新构建 `dist_new` 并重建后端，核对浏览器实际运行版本。真实 Harness 的连接 smoke test 只证明能返回文本，不证明研究、检索或 PPT 质量。

仓库根目录执行 `git diff --check`，审查每项待提交文件。个人配置、测试密钥、数据库和未经脱敏的结果不得提交；现有用户改动（当前包括 `CLAUDE.md`）不得顺带覆盖或提交。

## 8. 批次交付物与退出标准

### 第一批交付

- 隔离环境说明、来源核对表、代码/模型/Prompt/Skill 基线。
- W/Q/R/P 案例结果表，区分模型失败、应用失败、资料缺失。
- 报告、真实 PPT 文件、逐页视觉验收记录；所有未执行项目如实标注。
- 缺陷列表：证据、优先级、责任模块、修改建议、预期复测案例。

**第一批结束条件**：案例已经实际运行或有明确未执行原因，能据证据决定第二批修改，而不是泛称“感觉不好”。如果发现 P0，先停止受影响路径，修复后再继续。

### 第二批交付

- 仅处理第一批发现的必要缺陷，附回归测试与独立提交。
- 修复前后同配置/同来源案例对照；有配置差异就显式记录。
- 当前产品文档与运行行为一致，未完成和可选增强项独立列出。

**本轮完成标准**：

1. 无未关闭的 P0/P1；核心问题得到完整、可追溯且符合任务目标的回答。
2. 深度研究的子题、综合和证据覆盖可审查，已完成章节可恢复且不无谓重跑。
3. 预算硬限、空正文、轮次和超时错误均有准确状态与有限恢复路径，无同预算死循环。
4. 至少两种用途的 PPT 真实打开并通过内容/视觉检查，不以文件合法代替可用。
5. 正式书架、来源和个人配置未被验收污染；后端与前端回归通过。
6. 剩余 P2/增强项有清单，但不继续扩大本轮范围。

通过这些条件后进入正常使用观察，不再要求“再补一轮边界”才能算完成。有限并发、更多演示版式、可配置页数等按后续独立需求处理。

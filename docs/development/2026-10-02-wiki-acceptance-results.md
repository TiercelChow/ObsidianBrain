每例只跑一次。Q3 在同一会话执行三轮，检查数据库恢复的六条消息。来源为已审核语义 Wiki，不能把本轮结果推广成全局召回率。

首过程事件均在 6–11 ms 内收到；这是本机客户端接收时间，不是供应商生成时延。各轮流正文与最终保存正文一致，Q3 会话可恢复。Q3 第二轮仍附带扫描负载边界，范围收敛可进一步改善；第三轮按用户要求未再展开扫描批处理。Q2 也偏长，八篇小资料还不足以证明大书检索或答案精练性。

**增量体验失败原因已定位**：百炼接口直接请求可持续返回多个 delta（一次受控 256-token 小请求观察到 8 段，约 0.76 秒完成）；但安装版本的 Harness `dsh-acp` 用 `assistantUpdates` 转换已提交的 `session/event` 完整 assistant message，而非实时模型流。Rust 接收到的一段 ACP 文本如实传到 SSE，不能把这种结果描述成“真逐 token 流式”。解决方向是受控 Harness 实时事件桥接并处理最终提交/重试去重，不在前端伪造打字速度；本轮没有改写 Harness 的 Agent Loop。

验收工具观察到初始 `evidence` 在正文完成前已经到达。前端是否只在最终回答后展示需要另做界面验收，此记录不以传输事件顺序直接断言 UI 行为。

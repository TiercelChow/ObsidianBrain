## 1. 本阶段目标与边界

交付两个可以直接验证的闭环：

1. 从一本书建立按概念、实体、论断和关系组织的 Wiki；新增或修改资料时更新已有知识；问答中的有价值结论经过审核后继续积累。
2. 在问答或研究任务中选择 Skill，生成研究报告和真正的 PPTX 文件；支持进度、取消、重试、预览、下载及来源追溯。

保持既有约束：每本书独立知识库；知识内容及版本以 SQLite 为权威；原书只读；沿用 DeepSeek Harness 和现有第三方模型配置；章节索引保留为证据层与兜底。

当前进度（2026-09-14）：迁移 016 已拆分来源同步与 Wiki 编译状态并保护不可变历史；迁移 017 已加入版本化 Skill Registry、单书/用途绑定和运行事件；迁移 018 已加入语义变更集、审核、版本、成果文件、引用快照与研究任务交付状态。Markdown 来源可分批编译为跨章节候选，审核后原子应用；问答可回写候选；研究任务由持久化队列执行并可交付经结构校验的真实 PPTX。前端已覆盖编译/审核、实体结构、知识体检、Skill ZIP 导入、任务取消/重试、报告恢复和成果下载。

本轮没有把尚未具备的能力包装成已完成：DeepSeek Harness ACP 当前仍返回完整字符串，进度依靠持久化状态/事件和轮询而非真实文本 SSE；PDF 仍只登记来源，正文、页码与 OCR 属于 P2；ZIP Skill 仅接受指令与文本资源，不执行脚本；PPTX 在缺少生产预览依赖时标记“视觉预览未校验”。

已有 `docs/requirement/08-llm-wiki.md` 与 `docs/development/08-llm-wiki.md` 已规划两阶段摄入、变更集、Skills 和工具桥。本提案把这些尚未完成的能力排成下一轮可交付内容，并增加 PPTX 成果链路。原设计中的路线图不代表功能已经实现。

## 2. 调研结论

### 2.1 Karpathy 原文的核心

原文描述三个层次：不可改写的原始资料、由 LLM 持续维护的知识层、规定组织方式与工作流程的 Schema。摄入需要整合新资料与已有主题；查询可以沉淀新的综合结论；维护检查冲突、过时知识和缺口。原文还区分内容索引与时间日志，并将演示文稿列为可能的查询成果。参见 [Karpathy 原文](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)。

本项目采用数据库实现上述知识层：网页中的“实体页面”读取数据库 Markdown 字段；目录由查询接口提供；日志与版本由数据库维护。Markdown 是内容格式和可选导出格式，不作为第二份权威 Wiki。

还需优先处理两个版本问题：

- 当前片段 ID 由来源身份、章节位置、标题和片段内容计算，没有包含来源版本。文件其他章节变化时，未变片段可能与旧版本出现主键冲突。新设计必须显式区分文档版本与片段版本。
- 章节目前写入 `verified` 和 `confidence = 1.0`。提取成功仅表示文本可追溯，不表示书中论断已验证；需要分开“抽取状态”“知识审核状态”和“证据质量”。

## 4. 知识编译方案

### 4.1 数据分层

| 层次 | 内容 | 用途 |
|---|---|---|
| 来源证据 | 文档、不可变版本、章节/页码片段、原文快照 | 阅读定位、核实结论、编译失败时检索 |
| 语义知识 | 概念、实体、来源摘要、方法、比较、综合分析、待解问题 | 用户主要浏览的 Wiki；同一主题跨章节持续更新 |
| 知识结构 | 别名、论断、关系、引用、冲突、条目版本 | 去重、关联、更新影响评估、历史追溯 |
| 管理记录 | 内容目录、变更日志、运行与审核 | 对应原文索引和日志的数据库实现 |

页面类型由 Schema 模板决定。技术书可侧重概念与方法，小说可侧重人物、地点与事件；不强制每本书生成一套空类型。第一版提供通用与技术书模板，模板选择与单书覆盖可见。

关系先采用有限类型，如“属于”“依赖”“解释”“对比”“支持”“冲突”；关系必须注明来源或推导依据。别名匹配用于提出合并候选，不仅凭名字相同自动合并。

### 4.2 默认建库流程

```text
选择书籍、目的与模板
  → 扫描来源变化，建立可引用的证据层
  → 按来源分批分析，并读取已有相关知识
  → 跨章节归并概念、论断和关系
  → 生成新增 / 修订 / 合并 / 冲突候选
  → 服务端结构与引用校验
  → 预览变更、按策略应用
  → 更新知识目录、历史版本与运行日志
```

分析和变更提交采用现有设计中的两阶段方式。按章节分块仍可用于控制上下文，但每批分析必须查找已有主题，最终写入对象以语义主题为单位。长章节继续细分；不能只读取每章前几个字符、只取全书 Top 8，或把整本书塞进固定长度提示词后声称完整处理。

建议首版处理规则：

- 用户点击建库即授权在所选范围和预算内生成知识候选；默认批次预览后应用，可在建库前明确开启低风险自动应用。
- 新增带完整引用的条目允许按策略应用；冲突、合并、删除、替换人工修改内容强制审核。自动应用不等于事实验证。
- 服务端验证 JSON Schema、授权书籍、条目身份、源版本、引用范围和修订号；模型的自述不能代替验证。
- JSON 修复和模型重试次数受限；无效候选保留诊断，不进入正式知识。
- 每次提交具有幂等键与 revision 检查。每个已确认变更集短事务提交，避免长时间持有 SQLite 写锁。
- 同书编译串行，跨书并发受配置限制；新扫描与编译快照不同则标记过时，不能覆盖较新状态。
- 展示真实覆盖范围：已处理来源数、待处理数、失败数、知识条目数。无法客观计算模型内部进度时使用阶段状态，不生成虚假百分比。

### 4.3 章节兜底与渐进升级

提供两种显式模式：

1. **智能 Wiki（默认）**：证据抽取后进行 LLM 语义编译。
2. **基础章节索引**：不进行付费语义编译，可浏览章节；要生成自然语言回答仍需可用模型。

模型未配置、调用失败、预算耗尽、来源提取不完整时，保留证据层并显示失败原因及已完成范围。已有成功 Wiki 继续可读，仅相关条目标记待更新；不能用章节条目覆盖已有语义知识。

分别记录 `source_sync_state` 与 `wiki_compile_state`，避免一个“已就绪”掩盖只完成扫描。旧知识库标记为“章节模式，可升级”，由用户选择升级；不在迁移或打开页面时自动触发全书付费建库。

### 4.4 增量维护和知识回写

- 来源未变化：复用版本与片段，不调用 LLM。
- 来源变化：仅重分析变化来源，再沿引用和关系评估受影响知识；可能需要更新其他章节关联的主题，不限制为只改一篇摘要。
- 来源删除或不可访问：标记缺失，保留已归档证据；相关论断进入待核实，不级联抹除对话和研究报告引用。
- 人工修订：保留编辑版本和保护标志；后续模型更新提交差异供审核。
- 问答：默认只读。复杂比较或新综合结论提供“保存到 Wiki”入口，用户确认后生成变更集；简单问答和未经验证的猜测不自动入库。
- 研究：报告和文件可以交付，同时产生待审核知识候选。分别记录 `deliverable_state` 与 `knowledge_change_state`，文件成功不表示知识已应用。
- 检查：结构检查由程序完成；矛盾、缺口、过时结论的语义检查由 LLM 给出带证据的候选。检查结果能创建后续研究任务。

## 5. Skills：从指令扩展到可执行能力

### 5.1 产品内的管理方式

在现有 Wiki 配置中新增“Skills”，包括内置包、导入包、文件内容、版本、来源、权限、依赖与运行记录。首版支持本地文件夹/ZIP 导入及内容编辑；GitHub 固定提交导入在下一批补充，不能后台追随 latest。

`SKILL.md` 与其引用资源、模板内容存入 SQLite，运行时才物化所选版本。只注入可用 Skill 的名称和简介，需要使用时再加载正文与引用文件。第三方包不自动读取用户机器上其他 Agent 的全局 Skills。

区分三种兼容级别：

- 指令型：只需现有知识读取工具，校验后可用。
- 工具型：要求知识变更、联网或成果生成等特定能力；能力缺失则不可运行。
- 脚本型：需要 Node/Python/Shell 或额外软件；只有受支持的执行适配器和依赖检查通过后才可用。

输入/输出 Schema、适用场景、依赖清单和能力请求存放在本项目的 Skill 扩展清单中，不冒充 Agent Skills 标准字段。第三方包未声明这些信息时标记“待适配”，导入成功不等于可执行。

配置层级沿用：系统默认 → 场景模板 → 单书覆盖 → 单次运行。问答输入区域提供 Skill 选择；研究创建页同时选择“任务目标”和“交付物”。自动选择只限已启用且权限匹配的 Skill，并在运行中显示实际使用项。

### 5.2 首批内置 Skill

| Skill | 主要用途 | 交付物 / 写入方式 |
|---|---|---|
| `book-ingest` | 新来源语义分析、跨章节合并 | 结构化变更集 |
| `book-query` | 知识优先问答、证据核实 | 带引用回答，可选知识候选 |
| `book-lint` | 检查缺失引用、重复与冲突 | 检查报告、修复候选 |
| `book-research` | 确定研究问题、检索与综合 | 研究报告、知识候选 |
| `book-presentation` | 将研究结论组织为演示文稿 | PPTX、预览、引用清单 |

先做上述端到端能力，再增加 Word、表格、测验、学习计划等。PDF 抽取首先是程序可验证的来源适配器，不能仅用名为 `pdf-extract` 的提示词替代。

### 5.3 Harness 与权限边界

保留 DeepSeek Harness，增加小型适配插件和受控 HTTP 工具桥，沿用原 Agent Loop。继续支持当前第三方供应商、Base URL、模型与密钥环境变量配置；不要求切换到 DeepSeek API 或 Claude 模型。

首轮技术验证应确认固定版本的 Skill 加载、自定义工具、取消、事件与 Usage 能力。若当前固定版本不足，先做可回退的版本升级验证；最新上游文档只用作调研依据。Claude Code Adapter 后续复用同一工具契约，不与本轮核心交付同时全面实现。

工具能力分组：

- `knowledge.read`：列目录、搜知识、读实体、查关系、读取版本化来源片段。
- `knowledge.propose`：提交候选变更；没有模型直写 SQL 和直接覆盖正式数据的接口。
- `artifact.render`：把经过校验的结构化文稿交给受信任生成器。
- `artifact.read`：查看本次成果、校验与预览结果。
- `web.research`：后续显式开启的外部检索与来源登记；默认关闭。

工具请求使用短期 Run Token，服务端强制限定知识库、工具和操作范围。Skill 文件、书籍正文和外部网页都是待处理数据，不能扩大授权。参数中的其他书籍 ID、路径和 URL 均需校验。

首版不开放任意 Shell 来运行陌生脚本。PPT 使用结构化 `PresentationSpec` 加受信任生成器，避免让模型生成任意宿主代码。生成子进程只继承必需环境变量，不向其传递模型密钥；限制时长、内存、输出大小和输入资源范围。

独立临时目录不是安全沙箱。后续开放通用脚本需要实现并验证各平台的文件系统、进程、网络边界；平台不支持时明确禁用。ZIP 路径穿越、符号链接、超大展开体积、远程资源访问与恶意内容均列入测试。

### 5.4 PPTX 首个成果场景

示例：“根据这本书制作一份 10 页的技术分享 PPT，面向初学者，包含核心概念、关系图和注意事项。”

```text
确定受众、页数、重点、模板和来源范围
  → 检索 Wiki，按需核对原始证据
  → 形成研究结论与逐页大纲
  → 生成结构化页面内容及引用
  → 受控生成器输出 PPTX
  → 文件结构检查、内容检查和逐页预览检查
  → 保存文件、预览及任务结果
```

第一版支持有限但完整的模板：封面、概念说明、双栏比较、关系图、数据图表、总结。模型输出结构化数据，生成器负责排版和格式；失败时保留研究报告与大纲，不能将“PPT 大纲文本”标为“PPT 已生成”。

交付标准：

- 真正可打开的 `.pptx`，正文和基础图形可编辑；复杂公式或图形若转为矢量/位图需说明，不承诺全部对象可编辑。
- 支持项目配色的默认模板；每页关键论断附可追溯引用，讲者备注保留来源标题和位置，避免只有离开本应用就失效的内部 ID。
- 使用真实来源数据；没有数据时不编造图表数字。外部图片、联网与图像生成分别授权，不隐式增加供应商调用。
- 结构校验、引用检查、溢出/重叠检查和渲染预览独立记录。缺少预览依赖时显示“文件已生成，预览未校验”，不标为完整验收通过。
- PDF/缩略图预览根据生成环境能力启用。手机端浏览预览与下载，不在移动浏览器内执行文稿生成脚本。
- Windows x64、macOS arm64/x64 验证 Node 运行、中文字体、生成与预览能力；Office/Keynote 的实际打开测试不可用“LibreOffice 能渲染”完全替代。

文件归档采用“SQLite 元数据 + 应用受管附件文件”。知识实体、Skill 内容和版本仍全部在数据库；PPTX/PDF/图片属于二进制成果，不是磁盘 Markdown Wiki。附件记录哈希、类型、大小、Run、Skill/模板版本与引用快照，采用暂存校验后归档，备份/恢复同时覆盖数据库和附件。

## 6. 用户页面调整

复用现有页面壳、搜索、选择器、弹窗与移动端容器，不引入新的独立样式体系。

| 页面 | 下一版展示与操作 |
|---|---|
| 知识库管理 | 区分来源同步与智能编译；展示覆盖度、知识数量、待审核、失败原因；提供升级旧章节库和继续失败批次 |
| Wiki 工作台 | 默认展示主题知识；章节移入“来源”分区；实体详情包含正文、关系、引用与版本；提供变更预览及审核 |
| 知识问答 | 可选 Skill；显示“检索知识 / 核对来源 / 生成回答”等真实阶段；来源原位预览；可保存知识候选或转研究任务 |
| 研究任务 | 分开展示目标、运行步骤、报告、成果文件、知识变更；成果卡可预览、下载和重新生成 |
| Wiki 配置 | 新增 Skills 管理及依赖检测；分别配置建库、问答、研究的模型和预算；显示继承来源 |

移动端优先单列：报告阅读、成果预览、引用查看独立展开；长任务离开页面后继续，返回能恢复状态。操作入口控制数量，沿用系统既有组件。

## 7. 共享运行与成本能力

- 把同步 HTTP 等待升级为持久化 Run/Job：创建返回 Run ID，后台执行，事件入库，前端 SSE 订阅并可断线恢复。
- 状态包含 queued、running、waiting_review、completed、failed、cancelled；服务重启后未终结任务按检查点恢复或标记中断，不误报成功。
- 取消中止后续工具及模型调用；模型服务已产生的费用不承诺撤销。重试按步骤去重，不重复应用知识变更或重复归档文件。
- 记录公共阶段和工具摘要，不暴露模型私有思维链。真实文本 delta 必须来自适配器事件；仅能拿到完整回答时展示诚实的等待状态，逐字动画不计为后端流式能力。
- 按实际调用记录 Token；一个 Run 内的多轮、工具返回和重试需能归集，失败运行已有上报用量也计入。供应商未上报时保留 `estimated` / `unavailable`，不能与账单实测混为一谈。
- 筛选扩展为日期、书籍、调用方、Skill、模型和运行状态。调用方包含建库、问答、研究、维护；按日统计使用明确时区。
- 优先补充供应商回传 Usage 的适配器能力。无法获得时，预算属于估算保护而非账单硬上限；费用估计还需要配置可靠的模型单价。
- 每书首轮默认单任务执行；按变化来源缓存分析，不启动空闲循环建库。限制同时生成预览的任务数量，预览按页懒加载，避免再次放大手机内存占用。

## 8. 开发顺序与模块拆分

按依赖推进，第一轮总体交付必须同时覆盖语义 Wiki 和 PPTX，不只交付基础设施。

| 顺序 | 开发内容 | 主要落点 | 验收出口 |
|---|---|---|---|
| 1，P0 | 保护现有数据；增量来源与引用版本；拆分状态 | `book_wiki_store.rs`、`book_wiki.rs`、新迁移与回归测试 | 无变化同步不丢历史；修改一章不报片段主键冲突；书架数据不变 |
| 2，P0 | 固定版本 Harness 能力验证；Run Worker、工具桥与最小 Skill Registry | `deepseek_harness.rs`、新增 runtime/tool bridge/skill 服务和 Profile | Skill 可发现、可加载；可按授权查库；越权拒绝；取消及重连有效 |
| 3，P1 | 语义摄入、变更审核、跨章节归并、章节兜底 | 新增 ingestion/mutations 服务；扩展 entries/claims/relations；Wiki 工作台 | 同一概念跨章节形成一个可追溯主题，后续摄入更新原条目 |
| 4，P1 | Wiki 优先问答、知识回写、基础 lint、研究报告 | `KnowledgeChat.vue`、`KnowledgeTasks.vue` 与后端 query/research 服务 | 回答使用语义条目与原文；批准后才应用知识候选 |
| 5，P1 | Skill 管理完整 UI；PPTX 生成、验证、成果存储和预览 | `WikiSettings.vue`、任务成果组件、artifact 服务与受控生成器 | 真实生成可打开的中文 PPTX，刷新后报告、文件和来源仍可恢复 |
| 6，P2 | PDF 文本抽取与页码证据、进一步健康检查、外部研究、更多 Skill | source adapters、维护任务与扩展包 | PDF 可参与同一知识流程；联网只在授权后启用 |

第 3 步结束可先演示“跨章节 Wiki”；第 5 步结束演示“Wiki → 问答/研究 → PPTX → 知识候选”的完整版本。若下一次验收书籍选用 PDF，则将第 6 步的“PDF 文本抽取”前置到第 3 步；扫描件 OCR、复杂版面与图像理解仍单列，不混报支持。

新增数据模型优先补全原设计：entry_versions、change_sets/reviews、skills/skill_versions/skill_files/bindings、agent_run_events。按需新增 compile checkpoints、artifacts/artifact_citations、llm_call_usage。复用现有知识实体与来源表，避免平行建一套不互通的数据模型。迁移编号实施时取下一个未占用编号。

全书自动图谱布局、跨书自动融合、通用脚本市场、任意 Office 模板编辑、多 Agent 并发研究、扫描件 OCR 与多模态全面支持不作为本轮前置条件。

## 9. 验证方案与发布门槛

### 9.1 语义能力样例

使用独立测试书籍：三章分别介绍某概念的定义、应用和限制，使用中英文别名，其中两处论断存在条件差异或冲突。

预期结果：生成同一主题的综合页面；保留三处引用；解释适用条件，未能消解的冲突进入审核；新增第四章后修订同一条目而非创建同名副本；问答能找到跨章节联系。

构建质量使用人工标注的概念、关系、引用和冲突样例评估，并与章节模式做同题比较。实体数量增加和 JSON 校验通过都不能单独证明语义效果改善；不以模型自报置信度作为正确率。

### 9.2 自动化测试

- 来源：不变、变更、删除、重命名、空文件、超长章节、混合代码围栏；保存覆盖度与失败原因。
- 引用：同步前后对话和研究引用不变；历史内容来自当时版本；来源缺失仍可展示已保存证据。
- 编译：同义词合并候选、跨章节主题、冲突保留、非法引用、无效 JSON、过期 revision、幂等重试、原书提示注入。
- 降级：模型不可用和预算耗尽时保留章节与已有 Wiki；恢复模型后可继续；不会偷偷重跑已完成批次。
- Skill：版本固定、资源缺失、越权工具、路径穿越、压缩炸弹、缺依赖、跨书访问、运行中修改包不影响快照。
- 任务：刷新、SSE 重连、取消、超时、服务重启、知识审核与文件完成分离；用量不漏掉有上报的失败调用。
- 成果：真实 PPTX 结构、页数、中文、图表、引用、文件存在与哈希；预览缺失不能误判完全成功。

### 9.3 用户数据与发布安全

- 所有自动测试使用临时数据库、临时书架和临时源文件；禁止复用正在运行的应用数据做夹具，不向用户书架插入演示书。
- 迁移前使用 SQLite 一致性备份机制保存可恢复快照；验证真实历史结构的脱敏副本后再升级。
- 不清空书架、会话、任务、配置或既有知识库；旧引用无法完整修复时明确标记缺失，不能伪造历史内容。
- 保留旧章节模式兼容读取；发布回退包含应用版本与数据库/附件快照，而不是让旧程序直接读取不兼容的新库。
- 后端执行 fmt、clippy 和测试；前端执行类型检查、单元测试及生产构建；跨平台 PPTX 实际打开与手机预览单独验收。
- 功能验收后同步更新需求、开发设计、README 和 website 使用手册，明确“已支持”“需依赖”“计划中”。

## 10. 下一轮完成的判定

用户可以从现有书架选择一本 Markdown 书籍，在不损坏旧数据的前提下升级为智能 Wiki，看到跨章节知识及引用；随后发起一个研究任务并选择演示文稿 Skill，获得可打开的 PPTX 和可恢复的任务记录，同时自主决定是否将研究结论写回知识库。

这两个流程跑通，并通过失败、重复同步、取消与历史恢复测试，才算本轮完成。

实施结果：上述 Markdown 纵切已经在代码和自动化测试中打通。PPTX 包通过 OOXML 结构测试，并在开发环境使用 LibreOffice 实际打开及转换；Windows Office、macOS Keynote 和手机端文件预览仍需在对应真实设备进行发布前人工验收。
